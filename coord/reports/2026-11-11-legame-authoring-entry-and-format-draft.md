## 1. 本轮设计对象

先形成“设计一局”的通用工作流：用户在 Vit 启动页，或在其他 agent 中，围绕同一份设计文档讨论目标、环节、工程布局、材料与引导方式；Vit 将文档检查并装配成一局；进入工程后，LLM 围绕当前环节引导用户完成音乐任务。

乐局不限于教学。音乐任务目标为必填，学习目标按需要填写。教材、曲目、班级与教学法属于某一局的内容，不写死在通用入口和格式中。本轮不填写展演模拟课的内容。

乐局文档是随工程生效的工作约定：进入、重开、换模型或换会话后，由宿主自动把所绑定版本的目标、规则和当前节点提供给模型。普通创作局可允许模型主创；教学局通过教师发布的节点策略收紧协作，不能依靠学生本轮提示词改写。文档自动加载与执行权限强制是两层工作，不能只靠高优先级提示词宣称防代做。

## 3. 产品入口：同一份文档，两条设计路径

### 3.1 在 Vit 启动页设计

用户可直接说“帮我设计一局乐局”。设计动作优先进入设计对话，不被识别成普通新建工程并立即进入 DAW。

1. **讨论**：了解音乐任务、参与者、已有材料、想保留的自由度。已有信息不重复问；暂缺项记入文档。
2. **形成草稿**：AI 按统一模板写入设计，用户可在对话中增删、调整环节，改变参与分工及轨道布局。每次修改更新修订号。
3. **预览**：同一文档呈现为“目标 + 环节顺序 + 各环节材料/产物 + 工程布局 + 还缺什么”。首版用文本和列表即可，不以前置一个拖拽编辑器为条件。
4. **检查与准备**：检查文档完整性、材料实际可读性、音乐坐标和本机能力；展示可用项与缺口。讨论草稿无需先新建音乐工程。
5. **创建并进入**：用户选择“用这一版创建乐局”；成功装配到独立工程后走既有 Godot 进入链路。进入后 LLM 基于已选版本开场，从第一环节引导。

保存草稿、导出文档和创建工程是不同动作；草稿未就绪也可以保存或交给其他 agent 继续讨论。

### 3.2 在其他 agent 设计，再带回 Vit

Vit 应提供“导出设计模板/说明”与“导入乐局设计”两个可发现操作，对话中的同义表达落到同一工作流。用户可粘贴结构化文档；有材料时导入包含设计文件和材料的目录/包。

外部 agent 得到：格式说明、模板；若可用，再附一份 Vit 导出的能力快照。能力快照只是某台机器某时刻的参考，不替代导入时检查。

外部设计稿与 Vit 内起草稿走同一道检查。仅粘贴文档时，不能把另一台机器的绝对路径当成本机已存在的材料；缺文件就补齐或采用用户认可的替代方案。

### 3.3 设计与游玩的区别必须可见

设计对话修改的是草稿；进入乐局后修改的是本局工程。游玩中的普通请求“这句再柔和一点”只改变音乐，不隐式修改教学目标或完成条件。用户明确要改设计时另存新修订，再决定新开或迁移。

教学局的教师发布规则另有可信身份和版本约束，学生不能将自己的修改稿替换为教师版。学生可以离开教学局另行自由创作，该作品的来源与验证状态须保留，不能冒充原教学任务的独立作业。

## 4. 格式选择：设计源文件 + 生成的运行卡

建议以 UTF-8 YAML 作为唯一的结构化设计源文件，暂名 `design.yaml`，拟议标识 `vit.legame_design.v0`。字段名固定，说明内容可用中文；Vit 可把它渲染成人易读的预览。

工程只需一份 `design.yaml`；宿主按它生成模型上下文及人可读预览，不要求再落一份 Markdown 文档。此前拟议的 Markdown 文件名只是沿用仓库 `legame` 内部叫法的临时命名，不是机制或标准，现取消。教师私有答案与未解锁评测材料不进入学生可读视图/包。

不要求用户手写素材哈希、工具实名、运行时 clip ID 或判定器参数。Vit 在准备阶段补齐这些绑定，生成现有格式的 `level.yaml` 及材料清单。生成件带设计修订号/内容指纹与构建记录；不能在生成件中偷偷改目标却让预览仍显示旧设计。

最小可携带单位：`design.yaml`；引用实际音乐/图片等材料时，再带同目录 `assets/`。无需每局都附一个预制工程，工程可由布局要求建立。本文与模板合起来构成当前可交给其他 agent 的讨论材料，产品内导出功能尚待实现。

| 字段 | 应写明的内容 |
|---|---|
| `schema_version / id / revision / title` | 格式、稳定身份、修订和标题。未知版本不按旧格式猜读。 |
| `brief` | 给谁玩、音乐任务及最终产物、先修条件、预计时长。 |
| `objectives` | 可观察的音乐任务/学习目标；学习目标可为空，但音乐任务不可缺。 |
| `materials` | 材料身份、文件、用途、来源定位；PDF 同时标 PDF 页码和印刷页码。用于播放/编辑的谱例需另有核实的音乐数据。没有外部材料时可为空列表，删除相关引用。 |
| `workspace` | 拍号/速度等设定、轨道/片段角色、初始内容、用户创作区与参考区。布局指音乐工作区及流程组织，不承诺任意自定义 GUI。 |
| `capability_requests` | 要播放、读取、编辑、分析或生成什么，以及缺失时如何处理；这是能力需求，不是可直接执行的命令。 |
| `checks` | 检查对象、标准、证据来源及判定方式；区分任务进度与学习证据。 |
| `flow` | 环节顺序、每个环节的目标、任务、材料、分工、自由度、指导、检查及卡住时的处理。 |
| `guidance` | 总体引导方式、帮助程度、允许探索的范围和回到目标的方式。 |
| `governance` | 用途、请求的协作档位、可信发布策略引用；身份和最终有效权限由宿主确认。 |
| `answer_workspace_policy` | 教学局受保护作答对象、现有学生编辑链、模型所有写路径禁令；可请求用户作答但不授予模型写权。 |
| `progression_receipts` | 节点推进必须持有可信检查回执，绑定当前任务/学生/节点/规则和作品修订。 |
| `progression_interaction` | 学生表达完成后检查，合法回执驱动自然反馈/推进；只在真实选择处询问，不强制逐题弹卡。 |
| `flow.nodes[].assistance` | 节点请求的帮助种类、模型可写区域与保留给用户的决定；不能越过教师策略。 |
| `answer_disclosure` | 自由表述审核或批准内容选择两种输出方式；模型示范已展示则保留帮助状态，不能当作同题独立作答。 |
| `evidence_recording` | 创作操作来源、模型帮助及版本检查点要求；实际完整度由运行时记录。 |
| `submission` | 固定提交快照，生成作业报表和关键上下文摘要，链接原始记录供复核；非教学局可不要求教师审阅。 |
| `completion` | 本局必需产物、必需检查、用户收局确认、学习记录与导出安排。 |
| `budget` | 轮次/调用上限和到限处理；中止保留作品与未完成状态。 |
| `pending_questions` | 尚待讨论/补素材/补判定的具体问题。可保留在草稿，发布前须处置阻塞项。 |

### 4.1 检查方式的语义

- `deterministic`：可客观计算的约束，例如与给定节奏匹配。必须绑定已注册的判定实现和实测输入；自然语言判据不能自行变成可执行检查。
- `rubric`：依据明确准则，结合工程片段、对话或操作记录作评议。须记录证据和帮助程度；证据不足保留“待复核”，不能用“学生说完成”替代学会。
- `user_judgment`：由人作出的审美、意图或选择判断。选择发生不等于技术条件满足，也不自动等于学习达成。

节点的 `complete_when` 引用检查 ID。阶段推进条件、作品完成条件与学习目标证据分别记录。同一条检查可以被关联，但不得把“工程有内容”改写成“掌握了知识”。

模板中的 PDF/文字来源与可播放的音乐材料分开声明。轨道预置只能引用可导入的音乐数据，不能把来源 PDF 当成 MIDI；材料间用 `derived_from` 记录转写来源，实际对应范围在准备阶段核实。

### 4.2 首版流程能力

首版建议支持**自定义顺序的必经环节**，环节内部由 LLM 自由对话、示范、追问、重试与指导。这样能够设计不同的课和共创活动，又与现有顺序节点机制衔接。

跨环节条件分支、自动跳关和任意循环图暂不写成已支持能力；若设计确需它们，准备阶段报告具体缺口，另作扩展决策。不得把分支悄悄展平成另一个流程。

## 5. 每个环节应向 LLM 交代什么

模型每轮应获得当前设计版本、总目标、当前环节、相关材料片段、工作区真实状态、已收集证据、未解决问题及可用能力。后续环节只带必要摘要，教材仅按已定位范围披露。

宿主每轮从工程绑定态建立上述上下文，不能依赖模型自己找到文件或只在偏离时才补规则。恢复或上下文压缩后仍使用同一发布版本。教学局实际权限由系统授权、教师策略、节点许可及音乐区域共同约束；来源记录在编辑/执行边界产生，不由模型事后自报。详细机制见配套护栏草案。

每个节点的引导定义至少回答：

1. 这一环节要完成什么音乐任务，与哪些目标有关？
2. 开始时怎样引入，需要观察/播放/比较哪份材料？
3. 用户要亲自作出什么音乐决定，LLM 可以执行或示范哪些部分？
4. 哪些要满足，哪些可以自由选择？用户探索支线时怎样接回作品？
5. 用什么证据检查？未达到时怎样逐级帮助，无法判断时交谁复核？
6. 完成后留下什么，怎样衔接下一个环节？

文档写目标、证据与指导原则，通常不写死逐句台词。LLM 可调整表达和帮助程度；不能自行删掉必需任务、替用户做出其必须作出的决定，或改写判据以推进流程。

## 6. 准备、试走与版本绑定

1. **格式检查**：身份/版本合法、ID 唯一、所有目标/材料/检查引用可解析，模板占位与必填缺项有明确报错。
2. **材料检查**：文件存在且可读，所选页/小节/片段实际存在；PDF 可读不代表音符已经转写。识谱或转写无法核实则列缺口。
3. **能力检查**：将需求匹配到本机实际能力，判定器逐项绑定。必需能力缺失则保留草稿；替代方案须显式呈现其影响，不能声称等价。
4. **内容预览**：确认用户看见的目标、环节、材料、分工与生成运行卡一致，学习评价无“点确认即学会”的偷换。
5. **独立副本试走**：证明工程可装配、节点材料可达、关键交互与判定可工作；不在用户要使用的正式工程上预演。静态校验通过不等于旅程跑通。
6. **按版本创建**：本局绑定确定的设计版本、运行卡及素材。设计后来改稿不热改正在进行的一局；新开局采用新版本。旧局继续使用旧版本；确需迁移须先定义状态/节点映射，不能静默清进度。

构建或试走失败保留原草稿及失败报告。创建中断需识别未完成的装配，不能把半成品绑定成可开始状态。现有按 `level_id` 缓存/绑定不足以覆盖这些版本语义，须作为实现范围单独处理。

## 7. 开发验收应证明什么

以下为未来实现验收目标，不是已完成检查：

- 在 Vit 内起草与外部导入同一文档，产生一致的目标、环节及完成条件。
- 草稿可保存、导出、再导入、继续修改；“设计一局”不会提前进入空白工程。
- 缺材料、未知能力/版本、无实现的检查有精确诊断，未就绪不宣称可开始。
- 创建后通过既有前端链进入新工程，LLM 能引用正确材料和当前环节；用户完成任务后读取工程证据推进。
- 用户问支线问题仍能回到目标；LLM 不越过学生应作出的关键决定。
- 创作题允许多个符合要求的结果；不能统一使用标准答案逐音匹配判所有创作。
- 修改设计不改变旧局；旧状态缺新字段仍可按旧语义加载，未知版本明确拒绝。
- 单元/集成检查之后，按 AGENTS 要求进行真实栈、渲染面和旅程烟测，退出码与覆盖边界入回执。

## 8. 推荐顺序

当前按展演最小范围推进：入口/源格式/功能检查语义 → 通过框架设计模拟课内容 → 一轮真实创作与反馈贯通 → 整课 → 轻量作业报表/摘要 → 真实栈验证与展演采集。完整安全权限、严格输出和完整来源审计不阻塞此顺序。

这一步顺序允许课程设计较早暴露框架缺口；不要求先开发一套大型课程编辑器再开始备课，也不把具体模拟课写成唯一可运行实例。

## 9. 给外部 agent 的可复制说明

> 请依据随附的格式讨论稿和 YAML 模板，与我一起设计一局 Vit 乐局。先确认音乐任务、参与者、材料和自由度，再组织环节。维护一份 design.yaml，按我的反馈修改并增加 revision；不要另写一份相互矛盾的流程。区分音乐任务与学习目标、节点推进与学习证据、客观约束与人的审美判断。使用稳定 ID 引用材料/轨道/检查。缺素材、无把握的曲谱转写、未知 Vit 能力和待定判据写入 pending_questions，不伪造文件/工具/验证通过。你产出的是待导入检查的设计稿；真正可运行由 Vit 检查并装配后确认。现阶段先设计通用入口和格式，不填展演模拟课。
