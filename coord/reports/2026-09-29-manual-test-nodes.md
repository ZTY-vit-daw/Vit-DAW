# 手测节点规划（2026-09-29 晚，用户裁定落档）

> 用户裁定：决策侧须主动规划手测节点；判据=**功能质变点**（该节点合入后，用户手测的体验/结果与之前有显著差异）才召集手测——不是按时间或用户空闲安排。手测入口纪律不变：用户从 Godot 拉起前端进工程（AGENTS §5）。

## 判据与原则

1. **质变才测**：内部数据链/重构/纯测试改动不叫手测；用户可感知的行为、渲染、旅程变化才叫。
2. **节点挂卡**：每个手测节点绑定触发条件（具体卡合入+验收通过）；建 IMPL 卡时把用户手测写进验收面（`[等待用户手测]`）。
3. **决策侧出步骤清单**：每次手测前给"预期差异+操作路径+观察点"三件套，手测结果回写卡面。
4. 手测不是第一道功能验证（渲染面有 E2E-WEBUI-1、旅程有 JOURNEY-1 门槛在前）——手测是**体验差异确认**。

## M1 手测步骤清单（预案，GUARD-1 验收后激活）

1. 环境：Godot 拉起前端 → 打开既有测试工程（含已装载素材的混音工程，参考音频已导入）。
2. 路径 A（queryengine 感知）：只读观察提问"帮我看看整体混音，只读不要修改"→ 观察 agent 回答是否含具体观察条目引用（频段/动态/声像证据），可追问"低频段具体哪些轨有问题"看精确性。
3. 路径 B（RLM 感知）：问"当前工程响度和我的参考比怎么样"→ 观察参考电平对比披露（RLM 投影输出）。
4. 路径 C（对照）：明确动作请求"把 Track 2 提升 1dB"→ 确认执行链照常（只读 guard 不误伤动作请求）。
5. 回写：差异点逐条记录（与 9 月中旬手测记忆对照），异常项开卡。
