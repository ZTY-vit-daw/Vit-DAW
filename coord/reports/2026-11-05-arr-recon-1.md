## 点① 音源控制面（核心）

### 1.1 总判定

**音源装载与控制通道在内核与 agent 两侧均已存在且 instrument-aware，"挂 instrument 无 agent 通道"（AIGC-DRUM-GEN-1 A1 结论）按当前代码面需要修正**：装载链完整可达（chat 层装载工作流 + rack_add_node + 语义索引 IsInstrument + 中文词表），真正的缺口是 **preset 装载命令（结构性，全仓零命中）、编曲语境引导（capability_pack 九 pack 零音源面）、装载后出声验证编排（从未在编曲语境真栈验证）** 三项。

### 1.2 内核面：instrument 支持现成且成体系

**插件索引含 instrument 标记**：

- `plugin_list_available` / `plugin_search` → `PluginRackControlService::handleListPlugins/handleSearchPlugins`（`VitApp/Source/Service/PluginRackControlService.cpp:3122-3149/3150-3181`）：遍历 knownPluginList 的 VST3 条目，每行经 `pluginDescriptionToJson`（:1355-1375）序列化，**`is_instrument` 字段已在返回**（:1372 `entry->setProperty("is_instrument", desc.isInstrument)`）。
- `pluginDescriptionMatchesQuery`（:1377-1398）为纯文本 token 匹配（name/manufacturer/category/format/path/identifier 六域拼接）；VST3 合成器的 category 字符串通常含 "Instrument"，故 `query:"instrument"` 多数可过滤，**但这是启发式而非结构化过滤参数**（无 `is_instrument:boolean` 过滤形参）。

**装载命令两条，均通用不排除 VSTi**：

- `instantiate_plugin`（PluginRackControlService.cpp:3183-3260）：track_id + plugin_path/plugin_identifier → `resolveExternalPluginDescription` → `createNewPlugin(ExternalPlugin)` → `track->pluginList.insertPlugin(plugin, 0)`。装载后写 `vit_template_role`（:3226 `VitPluginTemplateRegistry::inferTemplateRole`——synth 插件返回 "instrument"，见 `VitApp/Source/Core/VitPluginTemplateRegistry.cpp:28-29`），返回 plugin_id/plugin_name/template_role。
- `rack_add_node`（PluginRackControlService.cpp:3519-3640）：rack 图装载，**synth 默认落 Z2 区**（CommandDispatcher.cpp:1317-1328 `parseZoneIdOrDefault`：`plugin->isSynth() → "Z2"`，效果器默认 Z3）；zone 持久化到 `vit_zone_id`（:3602）。
- 两条命令在 CommandDispatcher 的注册面：CommandDispatcher.cpp:3353-3361（list/search）、:3365-3401（instantiate/get_params/delete/move）、:3399-3401 附近（rack_add_node 族）。

**引擎层 MIDI 轨↔instrument 路由（停止条件核验项）**：

- `editHasRenderableAudioContent`（`VitApp/Source/Service/VitProductionCoordinator.cpp:57-88`）：AudioTrack 上存在 MidiClip/StepClip **且轨 pluginList 有 `takesMidiInput() || producesAudioWhenNoAudioInput()` 插件** → 判定可渲染。渲染拒绝分支的错误信息原文（:835-838）："The project has no renderable audio content (MIDI tracks have no instrument)… **load an instrument plugin on the MIDI track** before rendering"——**内核引擎层明文支持并预期 MIDI 轨挂 instrument**（tracktion 模型：无独立 MIDI 轨类型，AudioTrack + MidiClip + 轨上 synth）。
- Zone 数据流拓扑：`VitApp/Source/Core/VitZoneBufferAdapter.cpp:23-38`——Z1（MIDI 域）→ Z2（instrument 层）`native_midi_to_instrument`；Z2 → Z3（效果层）`native_audio_flow`。

**instrument 参数面（plugin_grabber 体系内核侧已建）**：

- `get_plugin_parameters`（PluginRackControlService.cpp:3326-3444）：通用命令，按 template_role 产出 `recommended_groups`/`quick_controls`（:3410-3413）。
- instrument 角色的参数子面已定义：VitPluginTemplateRegistry.cpp:119-127（instrument_cutoff/resonance/attack/release/decay/sustain/oscillator 子角色）+ `VitPluginGrabber.cpp:231-232`（instrument preferredRoles 清单）——**"调亮一点/改包络"所需的参数级语义面内核现成**。

**preset 机制（结构性缺口）**：`VitApp/Source/Service/` 全目录 grep "preset" 零命令命中（唯一文件级命中 ProjectAudioSettingsService.cpp 为音频设备设置域，与插件 preset 无关）；CommandDispatcher.cpp 与 PluginRackControlService.cpp 均无 plugin preset/state 装载命令。**装载音源后选 preset：内核零命令。**

2. **但 chat 层装载工作流对 instrument 完整可达**：`agent/internal/chat/plugin_grabber_workflow.go`——装载命令 = `rack_add_node`（:124/:1028），**候选 IsInstrument 时 zone="Z2"、pluginKind="Instrument"**（:113-118）；候选搜索 `searchPluginLoadCandidates`（:458-497）合并语义索引与 plugin_search，语义腿 `semanticIndexPluginLoadCandidates`（:503-541）**`IncludeInstruments: true`，且 intent kind=instrument 时 `opts.Type="synth"` 专项搜索**。
3. **意图词表含中文音源词**：`agent/internal/workflows/plugingrabber/commands.go:55-67` `hasInstrumentPluginSubject`——synth/synthesizer/instrument/vsti/sampler/合成器/乐器/音源/MIDI乐器 全覆盖；装载动词词表（:20-31）加载/插入/加一个/添加。
4. 语义索引 instrument 面全套：`agent/internal/pluginsemantics/index.go:35`（IsInstrument 字段）、:63（IncludeInstruments 选项）、:168（is_instrument 解析+category 兜底）、:183-184（instrument 加权）、:215（**默认搜索排除 instrument**——需显式 IncludeInstruments 或 type=instrument/synth）、:303-305/:366-370（别名映射 sampler/piano/drum→instrument）、:440（中文别名合成器/乐器）、:529（type 值 instrument）。

**A1 修正结论**：装载通道存在且 instrument-aware（工作流级）；A1 原判定"无 agent 通道"与 catalog 注册（2026-05-19 起即有 spec）和工作流现状不符，推测其语境为当时（10 月初）该装载工作流尚未建成或指 Mac 端形态（A1-MAC-FORM-1）。**在卷依据修正为：通道在、编曲语境的引导与出声验证链缺**——`plugin_grabber_workflow` 的入口是插件装载/参数抓取意图（混音语义语境的 gating 见 :70-74"我不会因为宽泛的混音目标直接加载效果器"），编曲语境（"给这条 MIDI 轨配个钢琴"）能否路由进该工作流**未经真栈验证**。

**PCA/processorregistry 族适用性**：

- processorregistry 家族表（`agent/internal/processorregistry/registry.go:248-270`）= StaticEQ/BroadbandCompressor/Limiter/GateExpander/DeEsser/TransientShaper/Reverb/Delay/SpectralDynamics/Clipper/Multiband **全效果器 + GenerationShell**，无 instrument 控制家族。
- **GenerationShell = 装载型家族先例**（registry.go:270）：`CoverageVocabulary:["load_only"]`、`Planner:"load_admission"`、`TypedExecutor:"none"`——"只装不控"的 PCA 形态已验证可注册（processorintent/intent.go:47 FamilyGenerationShell）。音源若走语义化装载准入，**复制此模式即可**；若走显式命令装载（rack_add_node），**无需 PCA 家族**（catalog 直连 RiskConfirm 即达）。

- instrument 语义化控制（"把音色调亮"→instrument_cutoff 的 PCA 路由）：**无家族支撑，后位任务**；首版用 Tier 2 直控路径（explain_controls 的 quick_controls + set_plugin_param，catalog.go:1170 描述已载明用法）即可支撑参数级控制。

## 点② MIDI 编配级编辑面

### 结论：区域批量语义现成度超预期，缺口收窄为编排成本级（非能力级）

**裁定已亲核面（§五-17）之外的增量发现**：

1. **note patch 全 op 支持 region 目标语义**：`collectTargetNotes`（`VitApp/Source/Service/MidiService.cpp:406-452`）接受 `note_id/note_ids` **或 `start+length` region** 双目标形态；走它的 delete_note/move_note/resize_note/transpose_note/set_velocity 全部继承区域批量能力。即：
   - **整段移调** = 单 op：`{op:"transpose_note", start:X, length:Y, semitones:+2}`（无需逐 note 枚举 ids）；
   - **整段平移** = `move_note` + region + delta（delta_beats/offset_beats 形参，MidiService.cpp:685-713）；
   - **整段力度** = `set_velocity` + region；
   - **区域量化** = `quantize_region`（grid 枚举 1/4、1/8、1/16、1/32，MidiService.cpp:455-487）。
2. **区域整段替换**：`replace_region`（MidiService.cpp:624-670）——区域重叠旧音删除+新 notes 插入的原子组合，重写一段织体一步可达。
3. **clip 级编排全注册**：`clip.move`（**跨轨 move**，source_track_id+target_track_id）/`clip.clone`（跨轨复制）/`clip.split`/`clip.resize`/`clip.remove`（agent/internal/tools/catalog.go:1131-1135，全部 RiskConfirm）；内核 handler CommandDispatcher.cpp:2901-2918。
4. agent 侧披露完整：midi capability 工具集（goalrunner_chat.go:4935-4941）与 midi pack Tools（capability_pack.go:234-275，含 midi.transpose/quantize/replace_region 别名面）；clip 工具集（goalrunner_chat.go:4944-4950）。

**真缺口（编排成本级，全部可组合达成）**：

| 操作 | 现状 | 组合路径 | 建议 |
|---|---|---|---|
| 同 clip 内区域复制（duplicate 一段） | 无单 op | read_notes（区域过滤）→ 偏移 start → insert/replace_region（beat 加法偏移，LLM 可靠） | 首版靠引导；后位 QoL 命令 `midi.duplicate_region {clip_id, start, length, offset_beats}` |
| 跨轨声部铺排（一段铺多轨） | 无单命令 | clone_clip+move_clip（clip 级现成）；note 级=read+write_clip_notes 组合 | 首版 clip 级组合够用 |
| 多 clip 批量 patch | apply_midi_note_patch 单 clip 域 | 逐 clip 编排（循环） | 不加命令；LLM 循环可达 |

**判定：编配级批量操作无结构性障碍**；`midi.duplicate_region` 为唯一值得进后位清单的 QoL 新命令（估 0.5 天，内核+注册+引导）。

## 点③ 符号分析衔接：消费路径 = 对话轮内闭环，零新层

`analyze_midi_transformations`（256 报告点①草案）的编曲消费链路形态，本次锚定 prompt 组装面后完整闭环：

```
capability pack（midi pack 扩展 or 编曲 pack）
  → ModelSummaryForCapabilityPacks（agent/internal/tools/capability_pack.go:23；
     调用链 harness.go:995-999 ← goalrunner_chat.go:4375 agentLoopToolContext 组装）
  → agentloop state.input.CatalogSummary（agent/internal/agentloop/pull_entry.go:219-220）
  → system prompt "Available tool catalog:" 段
    （agent/internal/agentloop/message_loop.go:4278-4291）
  → 模型按需调用 analyze_midi_transformations
  → 工具结果（bar 锚定 findings + music_context_echo + LLMContext 字段族）直接进对话轮
  → 模型消费证据 → 编排 MIDI 编辑命令（apply_note_patch 区域 op / clip 编排）
```

**分析证据进入编曲编排的层 = 对话轮内**（工具结果→LLM 推理→下一步工具调用），无新投影层、无新编排器——与裁定"编曲智能来源=LLM 符号分析→编辑 MIDI"（用户裁定）和 256 报告"首版不做 peer 投影"定案吻合。与混音线的差异：混音走 mixboard/semanticorchestrator 语义路由（PCA 准入后 typed executor），编曲走 **agentloop 自由对话 + catalog 直连命令**（写入面 RiskConfirm 预览确认，policy.go 三级分类现成）——**编曲线不需要新建编排器**，pack 引导+命令注册即成链路。

**一个衔接要点**：分析返回的 `note_ids`（evidence 回指）与编辑命令的目标选择（note_id/note_ids）**同域可直接衔接**（同一套稳定 note id，MidiService.cpp:310-320 midiNoteToVar 的 id 字段）——"把第 3-4 小节的模进移高八度"= analyze（定位 note_ids+bar）→ transpose_note（note_ids 或 region）一步跟随，**证据→编辑的 id 桥现成**。
