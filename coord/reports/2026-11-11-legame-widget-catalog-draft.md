## 1. 组合方式

模型可以组合基础文字、输入、选择、按钮、布局和结果展示，也能在组合中嵌入预制音乐组件。模型通常输出结构化类型、参数、材料/工程引用和组件间数据绑定；组件代码、计时、播放调度、绘谱、连续编辑由前端执行。

例如“教材片段 + 一段讲解 + 左右两个谱例播放器 + 选择按钮 + 说明输入框”可以在同一个交互面组成；不要求为每种教学问法重写一张固定卡，也不要求模型生成一页 HTML。

YAML 规定当前任务允许/需要哪些交互、材料与完成条件；模型可根据学生回应组合界面。布局变化不能改变底层任务或让历史消息中的旧按钮作用到新工程。

## 2. 基础组件（优先复用 A2UI/现有交互卡）

| 族 | 最小用途 | 备注 |
|---|---|---|
| 文字与材料说明 | 标题、短说明、术语、引文、来源页码 | 显示教材定位与谱例关联，不能凭空编造来源 |
| 按钮与动作 | 试听、再试一次、提交、提问、打开谱面 | 用户动作进入已实现的处理器，不由模型自由拼执行代码 |
| 输入 | 文字、数值、滑杆 | 意图说明、BPM、音量等；单位与有效范围显式 |
| 选择 | 单选、多选、下拉、分段切换 | 四种旋律线、情绪方向、版本选择 |
| 布局 | 行、列、响应式网格、标签页、折叠 | 同一组件可出现在不同组合中；窄窗口自动排成单列 |
| 交互卡片容器 | 组织任务说明、音乐组件、输入/选择和动作按钮 | 属于组件目录；模型输出结构化声明，宿主提供可复用呈现与交互处理 |
| 状态与结果 | 保存中/已保存、检查项、进度、缺项 | 从实际服务状态生成，不把模型文字当保存成功 |

这些是目录能力需求，具体 A2UI 或 Vit schema 名称在接线时定；不能将需求表中的中文类别当成现有 SDK 完整覆盖的证明。现有 `interactionCardKit.tsx` 已有 text/number/range/select/actions 可复用；布局和音乐组件扩展需实现。

### 2.1 交互卡片与模型输出的分工

交互卡片归类为通用组件/容器；模型输出仍可携带它的结构化声明。两者分别是前端实现与模型使用方式，不是互斥选择。

- 模型输出普通文字用于解释，同时按目录声明卡片标题、子组件布局、数据引用、输入字段和已注册动作。
- 前端渲染卡片及其按钮、选择、输入、播放器或谱面工作台；计时、播放、编辑与提交处理由程序执行。卡片不要求每次由模型生成 HTML/JS。
- 用户操作产生结构化事件，携带卡片/实例身份、选择或结果、相关工程版本；需要解释或推进时再进入模型轮次。
- 卡片状态（可操作、处理中、已提交、过期等）来自宿主和实际操作结果。旧消息里的卡片可以回看，但不能把旧参数误提交给新节点或新工程。
- 模型根据教学/创作需要调用普通交互卡；既有运行时需要收集的确认/判断也可使用同一组件呈现，但是否必须收集由对应流程决定，不由卡片外观决定。常规节点检查通过仍可自然推进，无需强制弹卡。

因此同一消息可包含“解释文字＋一张卡”，卡内组合 A/B 播放、偏好选择、理由输入与提交；也可以只显示播放器或谱面，不要求每个音乐组件都套一层卡片。

## 3. 三个主要组件与共享对比模式

保留用户已确定功能，将随谱播放、节奏编辑、旋律编辑与辅助视图合到同一谱面工作台；普通文件试听维持轻量。

| ID（拟议） | 控件 | 用户做什么 | 模型/系统收到什么 | 范围 |
|---|---|---|---|---|
| `audio_player` | 轻量文件播放器 | 点播放、暂停、拖进度、查看时长 | 材料身份、真实播放状态及必要事件 | 播放器为 UI＋内核后端适配，音频文件经内核预览平面播放（2026-11-12 更正）；不强制显示谱面 |
| `music_score` | 五线谱工作台 | 先写节奏，再赋音高；同一处看谱、编辑、试听、跟随、选段、循环、提交 | 目标 clip/region、保存修订、音符差分、当前选段和提交事件 | **展演必需**；节奏/旋律/read/edit 为模式，旋律线为推荐叠加层 |
| `beat_pad` | Tap/节拍面板 | 按键打拍，选择单位/拍号，标重拍并试听/应用 | 敲击引用、BPM、单位/拍号、稳定程度、实际应用结果 | **展演必需**；可独立或嵌入谱面工具条 |
| `mode: compare` | 双播放器 A/B 组合 | 两份通用播放器实例共享切换/互斥/位置规则，比较两版本 | 版本/范围、试听和选择/解释事件；采用版本单独记录 | 拆分旧整体卡形成组合组件，底层预览按需复用；适配未实现 |

### 3.1 旋律线视图对本课的作用

教材实践一要求四种旋律线形态，实践三要求运用旋律线组织八小节旋律。将五线谱上的音高起伏与可播放轮廓联动，能让模型说“看这段如何从平缓变成跌宕”时有具体参照。

作为 `music_score` 的叠加层，初版只显示学生已有音符或核实的谱例，不将画一条曲线自动生成好旋律设为必需。若给轮廓类别建议，保留依据和不确定性；几何轮廓不直接判定情绪或艺术质量。

### 3.2 本课以谱面节奏模式取代独立节奏格

本课不另做节奏格：在 `music_score` 内先以固定参考音高或节奏记谱写时值、附点和休止，保存节奏稿后进入旋律模式，在同一组事件上赋音高。修改节奏和修改旋律使用同一编辑器，不建立第二份节奏作业。后续鼓机或入门节拍教学需要时再加网格辅助视图。

对已有材料“慢放试听”和“实际修改时值/拍号”要分开呈现。前者是播放功能，后者会改变作品并需保存回读。当前拍号修改能力/特殊节奏是否可用，要在课例技术映射中确认，不能单凭控件画面声称可写。

### 3.3 A/B 比较对本课的作用

对照原片段与学生修改后的片段，比较哪种更贴近自己的意图。支持“都不喜欢/还不确定/继续改”，选择不自动证明学会，也不强迫模型替学生选择。

同一任务范围与两版本要显式绑定，播放使用真实后端时钟，避免左右同时播放。已有 audition 使用独立预览平面，应复用其时钟，不能误套工程播放位置。课堂选择只记录偏好，不触发现有混音的回滚/保留结算；需要适配，不重建 A/B 引擎。

组件结构按用户提出的“两个播放器”收敛为：通用播放器 A + 通用播放器 B + 共享比较控制。混音判定/作品采用由调用方处理；播放器自身只承担播放与比较事件。[拆分细节](2026-11-11-legame-widget-consolidation-and-reuse.md) §3.3 为最新设计。

## 4. 五组配套组合（主要拼基础组件和上表能力）

| ID（拟议） | 配套组合 | 最低内容 | 为什么需要 |
|---|---|---|---|
| `task_panel` | 当前任务面板 | 当前环节、音乐目标、固定条件/自由选择、相关材料、提交/求助 | 学生随时知道在做什么；不强制每题弹窗确认 |
| `material_target_picker` | 材料/工程目标选择 | 题目谱例、已有片段、当前选段；名称与真实 ID 对应 | 模型和学生指的是同一段，避免改错轨或放错版本 |
| `feedback_panel` | 检查与反馈 | 具体结果、对应小节、缺项、重听/回改/求助 | 把反馈连回作品，不只说“不错/不对”；复用谱面选择与循环 |
| `version_shelf` | 本局版本架 | 关键版本名称、时间、试听、差分、继续采用或复制为新尝试 | 防止示范/修改覆盖学生上一版；初版保留关键快照即可 |
| `submission_review` | 提交与回顾 | 作品、作业报表、关键上下文摘要、原始记录入口 | 完成本局，服务展演与教师复核；暂不建班级后台 |

用户新确认的 YuE2 按谱成曲，用上述基础组件增加生成卡组合：源谱版本＋风格提示词/选项＋生成动作＋真实任务状态＋结果播放器。不同版本用双播放器 A/B；音源选择/独奏试听放入谱面工具条。首版纯器乐，保留学生旋律条件，具体见[收尾设计](2026-11-11-legame-student-score-to-yue2-finale.md)。不为此另建一种自由生成网页运行时。

这些不是五套独立音乐引擎。任务与反馈主要是文本/状态/按钮组合；版本架用两份快照加播放器或 A/B；报告用已有记录组织。组件界面再轻也需要真实版本/记录接口，不能把前端缓存当工程历史。

## 5. 纳入已有组件的子功能

- **虚拟键盘/音高试听**：放入 music_score，可点击试听并输入选中位置，不先造完整键盘产品；MIDI 硬件输入可后续扩展。
- **音符时值工具条**：music_score 内含时值、附点、休止、延音及首课实际需用符号。
- **选段后提问**：在同一谱面或其旋律线叠加视图选择范围，“问 Vit 这段”携带结构化范围和问题，不靠截图猜指称。
- **慢放与循环**：共享播放控制适配，绑定当前实际后端时钟；不为每张卡造独立 transport。
- **前后差分**：可在 editor/contour/AB 中叠加，复用已保存版本数据。
- **保存状态和撤销重做**：属于编辑器正确性，不放到每道题各做一份。撤销要与内核提交语义一致。

## 7. 共用的数据与交互约定

以下是组件层设计要求，不是完整教学安全系统：

1. **共享身份**：surface/组件实例 ID + level/node ID + 工程/材料引用。当前工程、目标和版本由宿主核对，旧卡不能误写新工程。
2. **共享音乐数据**：notes/节奏/调号/拍号、稳定 note ID 与 clip 坐标。谱面的节奏/旋律模式、轮廓叠加和播放都映射同一份音乐事件及版本，必要的记谱信息额外保存。
3. **单一播放主控**：课程工程优先走 Vit transport；局外谱例预览有明确标识。面板之间共享播放位置与选段，不因模型拼了两个播放器就产生冲突。
4. **交互状态独立于模型轮次**：敲击、拖动、游标、选中与局部撤销由前端/服务处理。提交、完成敲击、要求解释或明确方案选择时才触发需要的模型轮次。
5. **传引用和差分**：模型调用不重复传页面代码、完整 MusicXML 或音频 base64；初次装载取数据，更新按实例发送变化，教学分析按需读小节。
6. **保存与回读**：持续编辑可先本地草稿，需明确标记；提交写内核并回读，得到工程修订后才显示已保存/检查。冲突或失败保留草稿，不能假成功。
7. **可恢复**：组件关闭、会话恢复后找回任务和已保存内容；未提交草稿与工程状态有清楚区别。旧消息可回看，过期动作提示而不执行。
8. **来源回流**：保留用户编辑、模型示范、提交和采用版本的实际事件，进入两份报告；无法归因的情况标记待复核，不假装已有完整逐音防篡改系统。

基础输入可由 A2UI 组织；复杂音乐组件的内部局部状态不需要每次上报模型。组件目录只暴露本阶段需要的类型和简短属性说明，降低输入开销。多组件同屏依然需要布局尺寸和事件绑定校验，不直接执行模型随意生成的网页脚本。

## 8. 一个组合示例（拟议格式，非已存在 API）

下例表达“学生先听两版、说明选择、继续编辑”，同时使用基础组合与预制组件。它不是完整乐局卡，也不能直接交给当前加载器运行。

```yaml
surface_id: example-rhythm-comparison
node_ref: <当前节点>
layout:
  type: column
  children:
    - type: text
      text: "听听这两个版本，你更想保留哪一种节奏？"
    - type: audio_player
      mode: compare
      left_ref: <原版本>
      right_ref: <已保存的修改版本>
    - type: choice
      id: preferred_version
      options: [A, B, 都不喜欢, 还不确定]
    - type: text_input
      id: reason
      label: "说说你的选择，或还想改变什么"
    - type: music_score
      mode: melody
      region_ref: <本题创作区>
    - type: button
      label: "提交这次修改"
      action_ref: submit_current_attempt
```

教师设计不需要填底层工具名或音符数组；引用由准备阶段绑定，模型按当前任务组合可用组件。最终使用 A2UI 语法还是 Vit 适配层由集成设计决定，不能把示意语法冒充 A2UI 标准。

## 9. 本轮建议与下一步

保持所有已确定体验：轻量音频试听、Tap、谱面编辑及随谱播放。主组件收敛为 audio_player/music_score/beat_pad；节奏和旋律编辑合并，旋律线作为叠加视图，A/B 从已有资源适配为共享模式。配套任务、目标选择、反馈、版本与提交回顾用基础组件组合，其他候选按课例需要再选。

先确定本课每环节“目标—音乐动作—控件—结果证据”，再冻结首课编辑/记谱范围和数据映射。设计过程中需要的控件可提前登记；不要求先开发全部目录才开始课例内容设计。
