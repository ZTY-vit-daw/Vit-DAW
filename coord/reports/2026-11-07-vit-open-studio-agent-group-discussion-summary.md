- 用途：供用户转交其他 agent，继续质疑、补充和比较方案。
- 状态：**讨论过程记录，已收口事项以[开放录音棚协作方案 v1（设计定稿）](../decisions/2026-11-07-vit-open-studio-collaboration-v1.md)为准。** 用户已确认总体方案并要求定稿落档；本文保留早期候选与质疑的演变，不作为当前未决清单或实施授权。

## 1. 讨论起点与产品定位

用户目前经常在 Codex、Claude Code、dsh 等 agent 会话之间询问、采集和转述意见。场景包括开发设计头脑风暴，以及未来的音乐制作企划。希望把这些参与者纳入共同讨论，减少用户搬运背景和观点的负担。

用户提出的核心定位：

> “vit应该要做的位置是一个各家agent能够来的录音棚，排练室。用户当然可以直接用vit，但是也可以用vit把codex，claudecode等agent连harness一起请进来。”

这里的重点是外部 agent 连同其 harness 参与：保留各自的执行循环、上下文管理、工具与技能，而不只是通过 API 召集几个模型模仿不同角色。Vit 自带 agent 可以继续作为直接使用入口和参与者，外部参与者也可以使用共同的音乐工作环境。

这一产品方向已由用户明确表达；各厂商接入方式、会话复用范围、默认参与机制等尚未定案。

用户随后进一步澄清：**Vit 的 DAW 工程与制作现场先提供公共上下文，群体进入这个录音棚/排练室，再将通用群聊的上下文投递、参与协调和调用选择经验用于其中。** 公共上下文不由聊天记录单独定义。详见文末 §11。

用户最新提出：在 Vit 工程中主动拉入一批 agent 时，可以同时触发这些成员各回应一轮，建立入群初始状态；后续再进行选择性参与。详见 §12。此处的一次入群首轮，与此前排除的逐消息全员持续推理不同。

## 2. 用户明确提出的群聊要求与质疑

### 2.1 @ 可以明确指定，但无 @ 时也应能自然参与

用户知道由主流协调其他对话流启动、接任务的方案，并提及已有 personal agent/bot 的类似机制。该提及是讨论背景，本会话未核验具体产品实现。

用户希望支持 @ 指定某个 agent 启动；真正关心的是没有 @ 时，群友如何表现出自然的注意力、主动性与分寸。

### 2.2 公共讨论记录先于成员调用

用户强调：输入先进入当前工程的群聊记录，再发生第一个回应。第二个回应者所承载的输入，需要包含已经发生的第一个回应，才能继续思考和回复。

如果多个 agent 预先拿到同一句用户输入，各自完成回答，再依次展示，仍然是群发征询，不能当成已经实现群思考。

### 2.3 后续思考必须能被其他人的发言改变

讨论中的新内容应实际影响后续参与者的判断、回应和行动。不能只是轮流输出完整答案，也不能通过延迟展示，伪装成成员读过他人的发言。

用户担心固定回合、固定顺序会很机械，并以此前常见的 LLM 竞技场为对照：各模型回答，再评判择优输出，并不能满足这里的群聊目标。

### 2.4 当前核心难题：第一位回应者如何产生

用户最新提出的问题：

> “光是我输入后第一个谁来触发回复这件事到底以什么样的条件逻辑来激活都很难。”

这仍未解决。把问题命名为“智能调度器”“注意力层”，本身不构成解决方案。需要说明判断发生在哪里、依据什么上下文、调用多少模型、如何纠错，以及为什么不会机械化。

## 3. 会话中形成的候选架构（Codex 建议，待讨论）

### 3.1 区分模型接入与 agent/harness 接入

| 接入对象 | 能力与边界 |
|---|---|
| 模型 API | 根据当前提供的资料与工具参与；相同模型不等于用户原来的 agent 会话 |
| agent 运行时 | 通过官方运行时接口保留其执行循环、会话、工具与权限机制；具体配置须逐端核查 |
| 用户现有会话 | 能否原地读取、继续或接入，需额外验证，不能由“支持 SDK”直接推导 |

建议同时考虑两个方向：

- 外部 agent 使用 Vit：Vit 通过 MCP 等接口提供工程观察、素材、试听与制作工具。
- 用户在 Vit 内邀请 agent：通过各家的运行时接口启动或继续会话、投递输入、接收执行事件与结果。

开放 MCP 工具不自动等于形成群聊；成员身份、消息投递、发言机会和会话生命周期仍需另行设计。

### 3.2 公共记录与各自会话并存

工程群聊记录保存公共交流及其来源：发言者、回复对象、资料引用，以及各回复所依据的讨论截止位置。客观工程状态、媒体与观察证据由 Vit 相应数据源提供，聊天中的主张不自动变成工程事实。成员保留自己的会话，参与时取得相关公共上下文，并补读新增发言。

共享内容可以包括创作意图、参考资料、候选方案、分歧、待验证问题与用户选定的决定。原始发言须可回查，摘要不能抹掉少数意见。

音乐场景中的引用应能定位到工程版本、轨道、时间范围或试听结果；需要区分成员实际收到的音频、测量信息与纯文字描述。

讨论可以形成制作企划或执行请求；工程写入仍经既有权限、准入与执行协调处理。多成员建议不意味着多成员可以同时修改同一真实工程。

## 4. “人味”与动态群思考的候选机制

Codex 将自然参与解释为：记得此前立场、认真接他人的话、因新证据改变看法、有新增价值才发言，以及关注未解决问题的后续。无需强制寒暄、固定扮演反对者或制造全员表态。

例如，用户说“副歌还是不够抓人”，A 提出改旋律；B 根据用户此前的偏好，建议先保留旋律、试伴奏留白；A 因此调整实验顺序；用户再明确旋律暂时保留。共同讨论状态随发言变化，而非从几个预先完成的答案中择优。

候选机制包括：

- 区分收到事件、判断相关、产生参与意愿、获得发言机会、公开发言；这些步骤不必等价。
- 每条公开发言、用户新约束或工具结果，都可能改变下一位参与者及其回应内容；不预排整轮 A→B→C。
- 成员可记录当前关注问题、等待结果与未解决异议，随讨论更新和失效，不按模型厂商固定职责。
- 被邀请成员可以发现意见已被覆盖、材料不足或无需补充，从而让出机会。
- 允许并发构思；发布前发现相关新消息时，补读并决定修订、放弃或等待。不能要求任何新消息都导致全员重来，也不能无视用户已经改变的约束。
- 无新增价值时等待用户或证据；独立征询、讨论分歧、整理企划可作为可选动作，不作为每轮必经流程。

这些机制尚未定义完整协议、阈值或预算，也未做可用性验证。

## 5. 首位回应者：目前仅有候选思路

Codex 最后提出的思路是“明确关系优先，模糊情况再做小范围语义判断”，不是用户已认可的答案。

1. 用户消息先入公共记录，确定性地触发一次处理；此时不必启动全体成员。
2. 如有 @、点击回复、尚待用户回答的明确提问等关系，优先考虑相关成员。自然语言回答的归属可能仍需语义判断，不能都视为免费、无歧义的程序判断。
3. 缺少明确关系时，由轻量判断机制读取当前输入、相关近期记录、未解决问题和成员状态，给出有依据的候选。
4. 候选成员读取实际讨论后，可以回应或让出机会；尝试次数需要有上限和兜底。
5. 公开发言后重新判断下一步，允许停止。

候选判断问题是：“由谁先回应，最可能增加有用内容？依据哪条已有记录？”允许多个合理人选，不要求证明全群唯一最优。

仍需挑战的地方：轻量模型是否真能选对；成员状态如何生成和更新；路由者会否形成偏见；候选拒绝是否带来额外延迟与 token；所谓让出机会是否只是另一种机械回合；用户输入无人回应时如何兜底。

## 6. token、延迟与计费的讨论结论及边界

- 用户目前手动向三个 agent 各问一次，改为 Vit 组织同样三次征询，用量可能相近；减少重复材料也可能节省输入。但从一个成员扩展到多个成员，通常会增加调用量。
- 真正的相互讨论会增加后续阅读、修订与调用；全员多轮读取完整记录容易放大成本。
- 连接、存储和普通消息路由本身不产生模型 token；真正由模型理解消息、判断后选择沉默，仍有调用成本。
- 全体自主判断与共享轻量筛选存在取舍：前者更接近每个成员亲自决定，后者便宜，但不能把路由器的估计描述成该成员已经读过并选择沉默。
- 只传新增记录可减少传输与重复组织；不保证模型不再计算或计费已有上下文。共享存储也不等于跨厂商共享推理成本。
- 缓存可能降低部分重复输入成本，受模型、前缀和有效期等条件影响；不能默认命中或免费。
- 控制成本的候选措施：按需唤醒、相关材料有界披露、限制自动讨论预算、普通程序承担路由、总结按需调用、复用工程事实与音频测量。
- 保留 harness 可能同时保留较大的指令、工具和历史开销，短回复不保证低成本；须测完整调用链。
- 用户自带客户端连接 Vit，与 Vit 内嵌厂商运行时的授权、订阅额度和 API 计费可能不同，不能承诺自动沿用现有订阅。

尚无原型测量，因此没有 token 节省比例、稳定性或延迟结论。

## 7. 希望其他 agent 重点讨论的问题

1. 无 @、无明确回复关系时，首位回应者应怎样产生？请明确输入、判断主体、启动条件、失败路径与成本，不只命名一个“智能路由器”。
2. 中央协调、成员分散判断、混合机制各适用于什么情况？如何避免主持者替所有成员决定兴趣和立场？
3. 如何让后来成员真正消费先前发言，又保留合理并发？补读、修订、取消与发布如何协调，避免旧答案排队展示和持续重算？
4. 成员的关注问题、此前立场、等待事件与忙闲状态由谁维护？如何避免陈旧画像、身份刻板化和维护成本失控？
5. 如何决定继续、插话、等待或停止？既避免全员重复附和，也避免重要异议永远得不到发言机会。
6. 如何验证“群思考”而非答案拼接？哪些案例能暴露机械轮流、路由偏见、忽视用户约束和假装读过消息？
7. 最小验证原型应测什么？如何分别记录路由、成员思考、工具调用、总结、失败重试的 token 与延迟，比较有效讨论的总成本？

建议允许推翻 Codex 的候选机制。用户此刻要求的是收集意见与继续讨论，没有要求直接实施或排入开发主线。

## 10. 后续调研与用户最新反馈（2026-11-07 补记）

上述为调研前的讨论记录。后续已核查群聊框架、跨 harness 应用和主动发言研究，见[现有群聊机制调研](2026-11-07-agent-groupchat-existing-mechanisms-research.md)，其中包含 DSH 生态具体项目及源码；不等于已验证用户本机 DSH 安装可直接接入。

用户阅读调研后明确：未发言成员持续推理的 token 开销过高，对目标产品不现实。默认方案不采用全员持续生成想法，也不采用每条新消息都让全员做“是否接话”的模型判断。仅隐藏回复或输出“无补充”不能视为解决成本。

用户认可优先研究三个组合：Microsoft 的公共历史同步与动态选人、agentschat 的跨 harness 会话及收件机制、DSH Agent Arena 的参与协调；Inner Thoughts 仅保留表达动机等概念参考，不照搬全员持续推理结构。同样不直接沿用 agentschat 的全员定时投递或 DSH Arena 的全员意愿判断。

新的研究焦点是：用有界调度成本选择并启动少量相关成员，同时保留成员依据最新公共发言继续思考的能力。首位选择、唤醒条件、预算和回退机制仍未定案；认可研究方向不等于批准具体架构、付费实验或生产实现。

## 11. 用户定位澄清：DAW 提供公共现场，群体进入排练室

用户进一步强调：

> “vit天生还是一个DAW，所以我才说这不仅是一个群，而且是一个录音棚，排练室，是一个群进入了这个排练室。所以vit天生携带公共上下文，然后才是他们的设计经验用进来”

这是本次讨论的产品前提。工程、素材和制作活动先存在；公共讨论关联其中的对象与变化，外部成员据此参与。不能把架构仅定义为通用 agent 语言环境中的多会话聊天室，再把 DAW 当作附加工具。

用户对三个参考的价值进一步明确：agentschat 提供持续讨论必需的上下文管理经验；DSH Arena 提供务实的管理员/参与协调经验；Microsoft 提供调用或不调用、选择成员的逻辑接口。它们作用于 Vit 已有的音乐工作环境，不能替代这个环境本身。

用户提出“可能可以让 Vit 的配置模型天然作为录音棚管理员”。当前记为候选：由熟悉当前现场的 Vit 模型承接协调角色。管理员的职责、是否每轮调用、预算以及与用户创作决定的关系仍待明确，未将其写成既定常驻调度方案。

由此派生的待讨论设计要点（Codex 整理，非全部已实现）：

- 公共上下文应能定位工程/媒体版本、相关轨道与时间范围、当前讨论或试听对象，以及创作意图、已有决定和未决问题。某成员实际获得的材料必须可追溯，不能因为对象在录音棚中就声称所有成员都已看过或听过。
- 权威工程状态与观察证据、用户的创作选择、成员提出的解释和建议保持各自来源；讨论结论不自动升级为工程事实。
- 沿用既有观察边界：DAD 事实与同级 peer 投影、CCB 的显式 view 请求与有界披露，不因群聊而全量展开 raw package 或将缺失/陈旧信息升级为可用。
- 调度可依据制作现场的明确对象与事件，例如哪份方案刚被试听、哪个实验完成、某问题等待谁的结果；事件登记与成员收件不等于立即启动模型。
- 共享现场减少每个成员从聊天重新猜测工程状态的需要，但成员读取所获上下文仍可能计费。群聊消息与工程变化均需适当引用、增量组织与按需展开，不能全量广播给全部 harness。

后续研究应先说明成员进入录音棚时能获取什么公共现场、如何获得它的变化，再讨论管理员与选择器如何据此安排参与。仍处讨论和资料整理阶段，不启动实现或付费实验。

## 12. 用户提出入群首轮：先建立观点，再组织续聊

用户提出新的交互方向：在 Vit 工程中把 agent 拉入群；同时邀请多个成员时，可同时触发这些成员各回应一轮，类似建群时的初始参与，再考虑后续讨论是否更易组织。

其意义是把开场变成用户明确触发的一次共同入场，不再要求系统在所有成员都尚未表达时猜出唯一首位。开场之后已有各成员实际贡献、关注问题与分歧，管理员可以据此安排下一位，而非只凭静态角色描述。

该方向与既定成本约束兼容：允许一次明确入群批次中的 N 位成员初始运行；不因此允许每条普通消息都启动 N 位成员，或每次新发言都让全员做接话判断。

由此可讨论的流程（Codex 整理，待进一步收口）：

1. 以当前工程焦点和用户议题准备同一份可追溯的入场上下文，用户邀请一批成员。
2. 这些成员各自作首轮回应，发言进入公共记录。并发首轮允许独立初步判断，不应伪称已经互相阅读；回应应围绕本次制作议题，不必强迫空泛自我介绍。
3. 管理员基于已公开观点、制作现场与未决问题，选择下一位或等待用户。被选成员补读同伴发言及工程变化后再回应。
4. 后续明确点名或交接可直接路由；开放情形使用有界选择。普通消息不自动触发全员，收件缓冲本身不启动模型。
5. 中途加入成员应讨论只初始化新成员、复用现有现场与讨论，避免重启整个群的首轮；首轮超时、失败和用户插话也需定义处理。

前文对项目“首批全员”的限制评价，是针对系统自动选择首位的原问题；在用户主动邀请的入场阶段，这一行为可成为适用机制。后续是否自然、选人是否合理、成本是否可接受仍未验证；本节不构成实现或实验授权。

### 12.1 用户认可管理员统一安排投递与唤醒

用户随后明确认可：管理员负责处理群聊消息该交给谁、提醒谁回复，各成员的公共对话投递与回复触发统一经过管理员协调。入群首轮也由该入口按用户邀请安排一批成员运行。用户之后进一步提出工具操作独立分支，见 §13；本节的统一入口不应扩大为每次 DAW 工具调用都经管理员模型判断。

为保持既有公共现场、群思考和成本约束，当前设计解释如下：

- 用户消息、成员原始发言及相关工程事件先由 Vit 保存并登记；管理员选择当前处理对象、投递时机与是否需要回应。消息尚未投递到某成员的执行轮次，不等于公共记录被删除。
- 成员被唤醒后，在授权范围内取得本次请求、相关未读讨论和工程上下文；仍能追溯其他成员原话，管理员选择不能把此前要求的公共上下文变成只有一条转述指令。
- 管理员作为统一调度入口可以包含普通程序规则与模型判断。明确 @、单一候选、无新内容、忙时排队等情况可由规则处理；模糊情形才进入受预算约束的模型选择，不要求每次投递都追加完整管理员推理。
- 成员完成后，原文与工件引用回写公共记录，形成下一次调度的依据。持续阶段不让所有成员自行读取新事件并启动推理。

本次认可的是统一协调入口；具体消息过滤范围、候选机制、上下文预算与管理员模型配置仍需收口，尚未启动实现。

## 13. 用户提出对话与操作分叉：外部成员直接使用 Vit

用户进一步提出应允许其他 agent 直接操作 Vit，并指出操作与对话输入需要分叉，操作不经管理员。当前记录为明确的产品设计方向；具体对外协议与权限接线尚未实现或验证。

### 13.1 两条入口，回到同一制作现场

- 对话：成员发言→Vit 公共记录→管理员安排投递/提醒→相关成员收到讨论上下文并回应。
- 操作：成员自身 harness 的工具调用→Vit 工具入口→权限与执行协调→DAW 执行→结果直接返回调用成员。
- 回流：执行回执与工程变化进入 Vit 的公共上下文；管理员可据此组织必要的讨论，但不逐条审批、转述或重新规划成员工具调用。

同一成员可在一次工作过程中读取现场、使用工具、检查结果并发言。工具结果首先满足原调用的执行循环，关键结果和状态变化另外成为公共场景信息；不将每次内部工具进度都转成唤醒全员的群聊消息。

### 13.2 对话管理员与执行协调的职责

用户所说的操作不经管理员，意味着不以管理员 LLM 的额外判断作为每次工具调用前置。成员工具调用仍使用 Vit 自身的权限、准入、执行与回执机制；操作权限依据用户授予的范围，不由群聊发言机会自动产生。

外部成员直接控制的是 Vit 提供的工具能力，可以通过 MCP 等适配或受支持 API 提供。各家 harness 保留自己的规划、工具选择和执行循环；Vit 负责真实工程操作的落地与结果，管理员负责群体交流节奏。

同一工程的并发写入必须由统一执行入口协调。当前可优先考虑并发读取、工程级排队写入，并对执行基线、回执与状态更新作核对；并行方案实验可另研究独立工程副本/分支。现有单进程租约不自动覆盖多个外部进程各自维护的私有租约，外部入口须汇入共同协调范围。

### 13.3 本次代码核对的复用基础与边界

以下仅为源码和现行文档核对，本次没有运行真实栈或外部 agent 操作：

- [chat/server.go](../../agent/internal/chat/server.go)：有 `/agent/tools`、`/agent/actions`、`/agent/invoke` 路由；`handleInvoke` 接收结构化工具请求，并执行权限模式等检查，不要求先走自然语言聊天选人。
- [tools/catalog.go](../../agent/internal/tools/catalog.go)：工具目录含输入 schema、是否修改工程、确认要求、撤销支持等元数据，可作为对外工具能力描述的复用基础。
- [executionruntime/coordinator.go](../../agent/internal/executionruntime/coordinator.go) 与 [writelease.go](../../agent/internal/executionruntime/writelease.go)：已有执行前置、持久化回执与工程级写租约；租约的 v1 范围为同一 agent 进程，不能直接外推为跨外部 harness 的全局互斥。
- [VSP Hub Extension API](../../docs/vsp/VSP_HUB_EXTENSION_API.md)：第三方 `role=extension` 有身份、状态与事件入口，默认拒绝 `command.request`。文档提出显式授权等扩展条件，但本次未验证完整外部写授权实现；不能把现有只读接入写成可直接开放全部操作。

需要进一步定义的内容包括：外部成员身份和项目绑定、授权范围、各类工具进入共同执行协调器的覆盖情况、取消与失败回执，以及操作结果进入公共场景的粒度。该方向不改变既有准入/验收门槛，也不授权当前讨论会话启动实现或操作真实工程。
