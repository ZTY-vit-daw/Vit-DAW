# 裁定：内核随窗就绪（kernel-ready-at-start）——用户产品裁定

- 日期：2026-11-15（手测 v6 进行中，用户口头裁定）
- 裁定人：用户（产品所有者）
- 记录：GLM 主管决策流

## 用户原话

「那这逻辑是不对的，应该是这个窗口启动时内核就已经就绪，并且连好 API，这样我才能新建或打开工程，agent 也才能正常进行对话以及控制管理工程。怎么能是放在打开这个行为上」

## 裁定内容

**VitShell 主窗启动时，headless 内核必须已就绪并连好 API**——不是在「打开工程」动作上才装载内核。启动台阶段的新建工程、工程列表、按名打开、agent 对话与工程控制管理，全部以在线内核为前提。

## 推翻/修正的对象

- [2026-11-15 VitShell 宿主设计](2026-11-15-vitshell-host-design.md) 的范围线「agent/内核**零语义改动**（契约不动）、『打开工程』→ agent/内核装载」——该线是 SHELL 宿主卡的**划界决策**（保持宿主卡最小），不是产品终态。本裁定将其修正为产品要求：内核生命周期提前到窗口启动。
- 旧链（Godot 先起、藏窗 → 拉起 agent → agent 连内核）本就有早期内核连接；VitShell 迁移宿主时内核链推迟到了打开动作。本裁定在新链上恢复并固化该行为。

## 证据背景（手测 v6 2026-11-15）

- 启动台阶段内核不在：列表/按名打开/新建走 `launcherRecentProjectPaths`→`KernelSendCommand`（`agent/internal/chat/launcher_flow.go:372`）必然降级报「连不上内核」；「最近工程」无限转圈。
- 烟测正式 run（SHELL-3）三轮 `greeting_text` 均为降级模板、`recents_count=0`——烟测即在无内核状态跑绿，覆盖未含「启动台内核在线」态。
- 抽屉「打开…」→文件对话框链不依赖预连接内核（内核随进工程拉起），仍可用——但该行为在本裁定后属于要被取代的过渡形态。

## 后续

- 任务卡 **SHELL-4（池序 360）**：内核随窗就绪改造+启动台真数据+新建链端到端+真栈烟测扩展（启动台内核在线断言腿）。
- 手测 v6 的「新建/列表」腿候 SHELL-4 合入后复测；v6 其余架构腿（单窗/进程树/打开关闭往返/全退）不受本裁定影响，照旧有效。
