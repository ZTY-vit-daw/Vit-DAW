# 手测 v3 判定 + 启动面形态产品裁定（方案 B）

- 日期：2026-11-14 深夜（用户手测 v3 后）
- 参与：用户本体手测；GLM 主管决策流记录
- 前置：v5.1 七卡（343-349）单晚合入后放行手测 v3（Godot 路径，autoload flag）

## 手测 v3 判定

**产品形态不合格（fail）**。用户实测：GUI 拉起后 web ui 默认优先在前面「等待被打开」——现状=Godot 主窗（启动页）+ React 顶层窗双窗并存，React 窗浮于前。机械面 8 点检查单未逐项走（形态否定即停）。

根因定位（主管）：
1. autoload 窗启动 URL=`/app/`（主对话面）而非 `?surface=launcher`（agent_chat_window.gd:46）——用户看到的是聊天窗而非启动台；
2. 343 只抑制了 start_page 内的 LauncherChatPanel，未抑制 Godot 主窗本身——双门面并存。
（注：这是 A 方案「窗口宿主」卡按卡面正确交付的结果——卡面即如此切分；形态裁决在卡面之上。）

## 产品裁定（用户）

**启动页只保留一个门面：方案 B——启动页=Web UI。**

- 启动阶段唯一可见窗=React 启动台（今晚 345/347/348 已建成的面）；
- Godot 主窗在 autoload 模式启动阶段隐藏，打开工程时才展开 DAW 窗；
- React/agent 不可用时回退 Godot 启动页（boot/fallback 链保留）；
- legacy flag（默认）行为完全不变。
- 方案 A（Godot 内嵌对话流窗）否决：将搁置 v5.1 React 启动台五卡投资、重启 341 类布局返工、双对话 UI 并存维护。

- 返工卡 `UI-ENTRY-1`（池序 354，P0）：单窗入口编排——启动窗路由 launcher surface + Godot 主窗启动隐藏/进工程展开 + 回退 + 同窗不重载切 surface（343 不变量保持）。
