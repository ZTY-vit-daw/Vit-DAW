# R1–R6 用户裁定单（通俗说明版，2026-11-18 晚）

> 背景一句话：每个乐局工程可以带一份 YAML“设计源”，描述目标、材料、轨道、检查等；系统要把它编译成运行时的“课时卡”。R1–R6 是编译前必须定下的六条规则；它们不定，W01（教学运行时第一块）就无法开工。下面每项都按“在做什么 / 为什么需要你定 / 选项 / 我的建议 / 例子”写。

## R1：普通工程要不要也能带一份“意图文档”？

- **在做什么**：工程包里可能放一个 YAML 说明“这个工程想做什么”。教学乐局是其中一种；将来普通混音工程也可能想写一句意图。
- **为什么需要定**：如果普通工程带的 YAML 被当成乐局文档去编译，会出错；如果完全不认，那普通工程就不能携带意图说明。
- **选项**：
  - **A（我建议）**：保留一个“普通工程意图文档”的版本号 `vit.project_intent.v0`，字段是乐局字段的一个最小子集（如标题、说明）；系统认出它后不编译成课时卡，也不报错。
  - B：现在只支持乐局；普通工程带 YAML 一律报错/忽略。
  - C：其他方案（你指定）。
- **影响**：A 是“先把门留好、暂时不用”，以后扩展不用改契约；B 最简单，但以后要支持普通工程意图时要改契约。
- **例子**：混音工程 YAML：`schema_version: vit.project_intent.v0`、`title: 我的混音练习` → 系统识别为普通意图，不生成课时卡、不报错。

## R2：系统靠什么判断“这是乐局文档”？

- **在做什么**：YAML 字段很多，需要一条规则决定“这份文档是不是乐局设计源”。
- **为什么需要定**：如果靠字段组合来猜，容易猜错；如果连版本字段都可以省略，系统就无法判断。
- **选项**：
  - **A（我建议）**：只看 `schema_version`，它必须存在；其他字段全部可选。
  - B：再加一个字段（如 `kind`）做第二道判断。
  - C：其他规则。
- **影响**：A 规则唯一、不会混淆；未知版本直接明确报错（fail-closed）。B 更灵活，但作者要多写一个字段，且两处要一致。
- **例子**：`vit.legame_design.v0` → 按乐局编译；`vit.project_intent.v0` → 普通文档；不认识的版本 → 报错提示，不猜。

## R3：YAML 里写的音轨，怎么对应到工程里的轨道序号？

- **在做什么**：设计源会写“旋律轨、鼓轨”；运行时需要给它们固定序号（1、2…）才能对应到工程轨道。
- **为什么需要定**：需要一种可预测、可排查的对应规则。
- **选项**：
  - **A（我建议）**：按 YAML 里的书写顺序自动编号（第 1 个=1，第 2 个=2…），编译时把“设计轨名→序号”映射记录在清单里。
  - B：要求每条轨道在 YAML 里显式写 `index` 字段。
  - C：混合：写了 index 用 index，没写按顺序。
- **影响**：A 手写最省事，映射可查；B 最明确但多写字段、容易重号/填错；C 规则更复杂。A 的风险是设计师调换轨道顺序会改变序号，但清单会记录变化，编译时能发现。
- **例子**：`tracks: [melody, drums]` → 旋律=1、鼓=2，清单记录；以后插入新轨导致变化，编译报告会显示映射变化。

## R4：一个教学目标有多条“检查”，怎么落到卡上？

- **在做什么**：一个目标可能有多条可验证要求（如“8 小节、四句轮廓、结束在主音”）。课时卡格式是一条检查对应一个目标。
- **为什么需要定**：这决定报告里能不能逐条拿出证据，也决定会不会出现“差不多算通过”。
- **选项**：
  - **A（我建议）**：拆成多个目标 `目标#1、#2、#3`，每条检查独立判定、独立记录。
  - B：选一条主检查，其余作为参考/辅助，不强制。
  - C：合并成一条综合检查（全过才算过）。
- **影响**：A 证据最完整、报告能逐条显示，代价是卡/步骤多一点；B 简化但可能漏证据；C 容易变成模糊通过。
- **例子**：“创作 8 小节旋律”拆成 #1 长度=8 小节、#2 轮廓=四句、#3 结束音=主音；学生/报告能看到每一条真实状态。

## R5：设计源没写速度/预算时，怎么办？

- **在做什么**：YAML 里的 tempo（BPM）和 budget（轮次/时间预算）可能空着。
- **为什么需要定**：速度和预算直接影响听感、判定和教学节奏，不该系统悄悄替人决定。
- **选项**：
  - **A（我建议）**：编译直接报错，要求设计者补写或显式传入覆盖参数（fail-closed，不偷偷给默认值）。
  - B：自动套用固定默认值（如 80 BPM、8 轮）继续编译。
  - C：tempo 报错、budget 用默认。
- **影响**：A 最诚实；B 方便但可能在演示时出现“不是我要的速度/预算”且没人发现；C 是折中但同理有风险。
- **例子**：YAML 没写 tempo → 编译失败提示“缺少 tempo_bpm，请补写或传 --tempo”；不会悄悄生成一个 80 BPM 的课。

## R6：三个小规则

### R6a 调号允许哪些写法？

- **在做什么**：设计源要写调号（如 C、F、G），决定记谱和生成。
- **选项**：A 自由写法（形如 `C`、`F#`、`Bb` 都行）；**B（我建议）固定 15 个大调列表**（C、G、D、A、E、B、F#、C#、F、Bb、Eb、Ab、Db、Gb、Cb）；C 大调+小调都收。
- **影响**：本课材料都是大调（F/C/G/D）；固定列表能防拼写错误和“不存在的调”，需要小调时再扩列表。
- **例子**：`F` 可以；`F#m` 现在会被拒绝并提示暂不支持小调。

### R6b 材料“小节范围”允许写单个值还是必须列表？

- **选项**：**A（我建议）单值和列表都接受，编译时统一成列表**；B 只接受列表。
- **影响**：A 作者手写更自然，内部格式统一；B 更严格但作者要多写一层括号。
- **例子**：`bars: 1-4` 或 `bars: [1-4, 9-12]` 都行，编译后都是列表。

### R6c 材料的“是否已核对”状态放在哪？

- **选项**：**A（我建议）只放材料目录 catalog，不写进设计源**；B 也写进设计源 schema。
- **影响**：核验状态会随工作进展变化；放 catalog 不会让设计源过时/耦合；B 会让设计源一改材料状态就要改文档。
- **例子**：材料从 `transcribed_unverified` 升到 `checked` 只改 catalog，不动设计源 YAML。
