## 1. VITNOTE 容器 UX 反馈（设计讨论项——用户明示"先讨论设计问题"）

- **正面上半场**：便签输入修复生效（"这次可以进行输入了，非常好"）+Q+拖圈选"效果也很棒"——V2 主链（圈选→胶囊→便签→输入→输出）用户实测可用。
- 反馈问题：①note 面板不可移动（实现面：⠿ 把手存在且拖动为轮询式健壮实现，但仅此一个 BaseButton 可发起拖拽——面板体/标题栏非按钮区域按下仍被 router→lane 消费，UX 上等于"不可移动"嫌疑大；待取证确认用户是否点过 ⠿）；②无缩放（V1 设计从未含 resize——设计缺口非回归）；③输入/输出区布局大小不合适（布局打磨项）；④收起后蓝色圆点（锚点）不可移动不可删除（V1 设计锚点仅"点击重开"，无移动/删除语义——设计缺口）。
- 处置：**转设计讨论**（用户裁定方向后再入卡）——候选方向：整标题栏可拖（非仅 ⠿）/面板 resize 把手或自适应高度/锚点可拖+可长按删除/布局重排。V2 设计 §3「容器沿用 V1」的边界正是此处，属 v2.x 容器升级面。

## 2. note 会话流架构（用户问"每 note 独立对话流是不是更好"）

- 现状：用户观察到 note 输入/输出出现在 webui 主对话流中（"同一个对话流"）。实现细节（chat_* 会话与主流的呈现关系）待取证。
- 决策侧意见（答复用户）：**赞成独立**——①语义：note=对辖区的一次性 observe 问答，混入主流污染主任务上下文（窗口占用+干扰执行链判断）；②UX：主流被插花难回溯；③note_id（note_<id>）天然可作会话键。需设计：note 面板内自含问答历史、主对话流不插花、远期升级通道（note→正式任务）衔接既有"v2 不做"默认。
- 处置：待用户拍板方向后入设计/实现卡（vitnote 会话域）。
