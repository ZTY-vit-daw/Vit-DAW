# 405 PLAN — first-visible normal work-area geometry (read-only design stage)

Owner /root/restore403; supervisor /root. This is a design-only handoff after accepted 403/404. Shared-main claim and card 405 were fetched/re-read before work. Current implementation baselines are main3b8a71d4 and frontendcdf1924; tracked status/diff were clean at entry. Four prior isolated shader-cache directories are retained and excluded. No source, production manager/GD/UI, old artifact, project or fixture was changed. No Godot/probe process, window, input, GUI or CUA was used in this stage.

## Evidence and observed mismatch
The accepted 404 raw records bind exact Godot `Engine` HWNDs and show a successful prepared hide + single `ShowWindow(SW_SHOWNOACTIVATE)` path. Before recovery, native `WINDOWPLACEMENT.rcNormalPosition` is `[519,245,944,556]` (425×311 outer pixels) while the observer reports logical/client viewport 720×480. After recovery the native outer rect remains 425×311 and client rect is 411×274. Thus 404 proves normal/noniconic/positive geometry/mode synchronization and foreground preservation, but not a large first-visible frame.

The 404 child was a GUI Godot 4.6.1 process. Its observer reports official hash `14d19694e0c88a3f9e82d899a0400f27a24c176e`, so the 720×480 logical size should not be read as physical outer pixels without a DPI contract. The 404 probe executable has no DPI manifest and no process/thread DPI setup; its raw `GetWindowRect` is therefore subject to Windows DPI virtualization. Official Godot 4.6.1 source snapshot shows `DisplayServerWindows::_create_window` uses requested logical `p_rect`, `AdjustWindowRectEx`, and work-area clamping; `window_set_size` adds decorations to a logical client size and `MoveWindow`; minimized `window_get_size` returns cached `wd.width/height`. It initializes process DPI with `SetProcessDpiAwareness(PROCESS_SYSTEM_DPI_AWARE)` only when `OS::is_hidpi_allowed()`. The deployed Godot manifest itself has no `dpiAware`/`dpiAwareness` entry; the exact source path is therefore the runtime code anchor to verify in a later run.

The 404 result has roughly 1.75 ratio between logical width720 and observed client/outer values, so DPI virtualization is a live explanation, not a conclusion. Microsoft’s GetWindowRect documentation explicitly says the returned rectangle is virtualized for DPI. `WINDOWPLACEMENT.rcNormalPosition` uses workspace coordinates for ordinary top-level windows, and Microsoft warns that workspace coordinates must not be passed to APIs expecting screen coordinates such as SetWindowPos. SetWindowPos `x/y/cx/cy` are screen/client coordinate parameters and `SWP_NOACTIVATE` prevents activation; `HWND_BOTTOM` moves a window to the bottom of the Z-order and clears TOPMOST if present. `SW_SHOWNOACTIVATE` displays a window at its most recent size and position without activation. These facts rule out treating a placement `rcNormalPosition` rectangle as direct SetWindowPos pixels and rule out “show then resize” as a first-frame proof.

The Godot 4.6.1 source’s `Window::_rect_changed_callback` accepts the DisplayServer rectangle as truth and updates the engine `Window` logical state. `DisplayServerWindows::window_set_size` refuses a maximized/fullscreen window, computes decoration deltas from `GetWindowRect`/`GetClientRect`, then `MoveWindow`s. The source’s `_create_window` computes an ordinary window rect from the requested logical `p_rect`, clamps position against `screen_get_usable_rect`, then calls `AdjustWindowRectEx`. These are relevant engine sync anchors; they do not prove the deployed binary’s exact branch beyond the recorded version/hash.

The old E2 production reference (`575dd713` `VitShell/main.cpp` and `godot_manager.cpp`) explicitly enables Per-Monitor V2 before creating its own host windows, uses the monitor work area, removes minimize/maximize style bits, calls a single hidden `SetWindowPos(... work rect ... SWP_NOACTIVATE|SWP_FRAMECHANGED)`, then a single `SetWindowPos(... SWP_SHOWWINDOW|SWP_NOACTIVATE|SWP_NOOWNERZORDER)` with a shell insertion target. That is a reference candidate only; it is not product authorization and is not copied into production by this plan.

## Single candidate order for a later runtime
The single candidate preserves 404's actual restoring API and moves geometry preparation into `WINDOWPLACEMENT`, rather than repeating E2's failed style-bit-clearing assumption:

1. Bind exact engine nonce/PID/seq/native HWND and CREATE/SHOW generation. Record all same-PID windows and establish safe iconic/no-child-FG/non-TOPMOST state. Record process/thread/window DPI awareness, `GetDpiForWindow`, monitor bounds/work area, both native rectangles, placement and engine logical sizes. Do not assert PMv2 merely because the old VitShell uses it; actual Godot is expected system-aware from source, and actual API values remain required.
2. Establish the single DPI/call-context contract in the table below. Geometry writes and their verification all run under `T`, the exact child window awareness context; PMv2 is a separate read-only physical audit. No target-logical rectangle is passed while the caller remains PMv2. The selected monitor and conversions must pass every declared round-trip check before staging.
3. Set temporary WS_EX_NOACTIVATE on only the exact disposable child and hide it with NOACTIVATE/NOZORDER. Copy its existing `WINDOWPLACEMENT`, set `length` correctly, clear restore-to-maximized/async flags, set `showCmd=SW_HIDE`, and set only `rcNormalPosition` to the computed target work-area placement rectangle. Call **SetWindowPlacement once while retaining hidden state**. This call is geometry staging, not the restoration candidate. Its effect on the hidden iconic state must be empirically recorded; no API/document assumption counts as proof.
4. While still hidden, stage z behind the owned guard via `SetWindowPos(child, guard, ..., SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE|SWP_NOOWNERZORDER|SWP_FRAMECHANGED)`; the external condition uses a visible self-owned passive guard prepared as specified below and never manipulates another application. Verify hidden/non-TOPMOST, baseline foreground retained, exact identity, staged normal placement exactly equal to the target, and guard-before-child z ordering. Do **not** require IsIconic=false yet; that was E2's unproved step. Do not clear WS_MINIMIZE/WS_MAXIMIZE manually or use SWP_SHOWWINDOW here.
5. Invoke **ShowWindow(SW_SHOWNOACTIVATE) once** as the sole restoring/presenting API. No subsequent resize or z repair is permitted. The first observed visible/noniconic state must already have the work-area outer rectangle in the declared coordinate frame and be behind the owned guard, non-TOPMOST and without child foreground/focus. If SW_HIDE staging unexpectedly creates a visible normal state, that earlier state is the first presentation and immediately fails the first-visible gate.
6. Keep native work-area rect/z order plus engine mode0/client-size consistency/zero child FG and baseline retention for at least2s. Logical client size need not equal outer work-area pixels; it must equal the independently measured native client after the documented DPI conversion, while engine mode/cache agrees. No code adjusts Godot mode or size during observation.

The unique candidate is therefore **exact identity/DPI conversion → protect+hide → SetWindowPlacement(SW_HIDE, target rcNormalPosition) → hidden behind-guard SetWindowPos without size/show → single SW_SHOWNOACTIVATE → ≥2s observation**. SetWindowPlacement is not asserted to be nonactivating by itself; child NOACTIVATE, baseline raw events and a fail-on-any-FG rule make that a runtime question. No alternative API order or fallback belongs to this budget.

### Exact DPI context and coordinate contract

`T = GetWindowDpiAwarenessContext(exactChildHWND)`; equality is tested with `AreDpiAwarenessContextsEqual`, not raw pseudo-handle equality. The proposed implementation must use an RAII-scoped `SetThreadDpiAwarenessContext(T)`, check its return, log the previous/current contexts and restore the previous context on every exit. It does not change the Godot process/window awareness. `P = DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2` is used only in a separate scoped read-only audit. No hidden implicit context switch is allowed inside a geometry helper.

| Operation/API | Calling-thread context | Input/output units and use |
|---|---|---|
| GetWindowDpiAwarenessContext / GetDpiForWindow / GetWindowThreadProcessId | record context; these identify target | Exact child HWND; no coordinate conversion |
| MonitorFromWindow(ownedGuard), GetMonitorInfo | P | Freeze monitor handle/device, physical `rcMonitorP` and `rcWorkP`; select once from the owned guard, not an external window |
| GetWindowRect / GetClientRect audit; ClientToScreen for both client corners | P | Physical screen outer/client-corner audit; client width/height kept separately from outer bounds |
| PhysicalToLogicalPointForPerMonitorDPI(exactChildHWND, corners) | T | Convert physical work/monitor corners to target-logical screen `workT` / `monitorT`; the HWND determines target awareness; never multiply by a guessed DPI factor |
| LogicalToPhysicalPointForPerMonitorDPI(exactChildHWND, converted corners) | T | Inverse audit only: must round-trip to the original physical corners within at most1 physical pixel per corner, with rounding recorded |
| GetMonitorInfo(selectedMonitor), GetWindowRect, GetClientRect, ClientToScreen | T | Target-context screen/client values. Contextual work/monitor rectangles must agree with the explicitly converted rectangles within the same declared rounding bound; disagreement rejects the coordinate contract |
| GetWindowPlacement | T | Ordinary non-TOOLWINDOW top-level workspace rectangle; copied only to placement staging/round-trip checks, never fed directly to SetWindowPos |
| SetWindowPlacement(showCmd=SW_HIDE) and immediate GetWindowPlacement | T | `rcNormalPosition` is `workT - deltaT`, where `deltaT = workT.topLeft - monitorT.topLeft`. This removes only the monitor's taskbar/workspace inset, not the virtual-desktop monitor origin. Readback must equal the staged placement rect exactly; retained normal/maximized flags must satisfy the frozen contract |
| SetWindowLongPtr(NOACTIVATE) / SetWindowPos(hide or insert behind guard) | T | No geometry input: NOMOVE/NOSIZE. Insertion uses exact owned guard HWND; no coordinate transform or external-window mutation |
| ShowWindow(SW_SHOWNOACTIVATE) | T | Sole restore/show; no coordinate argument and no placement call under P |
| Post-restore GetWindowRect / client-to-screen / placement snapshots | T, with separate P audits | Native target-space outer rect must equal `workT` within declared round-trip rounding; independent physical outer rect must equal `rcWorkP` under that same bound. Engine logical size compares to target-native client size, not outer physical size |

This is one write coordinate path: **P physical read → explicit HWND conversion → T workspace staging → T API calls → T/P independent readback**. It is not “convert to target logical then call SetWindowPlacement under PMv2.” The planned target is the ordinary outer `GetWindowRect` rectangle; DWM visible-frame bounds can be diagnostic only, because their non-client/invisible-border semantics differ and they must not replace the chosen acceptance rectangle mid-run.

The existing system-aware Godot path is supported only with a fixed monitor whose PMv2 guard DPI matches the recorded target/system DPI. Actual `T=SYSTEM_AWARE` plus mismatched monitor DPI is `coverage_insufficient/dpi_domain_unsupported`; do not emulate per-monitor awareness in Godot or silently rescale an unknown coordinate domain. PMv2 child is not assumed: it would be recorded as a different environment and requires supervisor review before changing the frozen single-domain experiment. An unaware/unaware-GDI-scaled target, missing DPI APIs, failed thread-context switch, failed conversions, readback disagreement, zero client bounds when a normal-window check needs them, TOOLWINDOW/owned/child hierarchy, off-screen/partially spanning target, or monitor ambiguity rejects before restoration.

Freeze selected monitor/device, monitor/work bounds, target awareness and DPI, owned-guard awareness/DPI. Recheck before staging, before showing and each sample. Monitor/workarea/DPI/context changes after freeze are `environment_interrupted/dpi_or_monitor_changed`; no migration/recompute/retry. An observed passive Godot DPI-change notification also stops the scene. Cross-process WM_DPICHANGED itself is not available through the current channels; do not claim it was intercepted or absent. A suspected transition that cannot be reconciled from frozen/repeated native readings and passive engine notifications is coverage insufficient.

### External foreground and owned passive guard

The owned guard is **visible, normal, non-TOPMOST and on the frozen target monitor in both conditions**, so “behind guard” always has an actual visible z-order reference. Synthetic: create/show the owned guard and make only that guard foreground before child spawn. External: first record the naturally existing external FG; create/show the owned guard using its own WS_EX_NOACTIVATE + SW_SHOWNOACTIVATE, place only the guard at HWND_BOTTOM with NOACTIVATE, and verify that the external FG HWND/PID has not changed. Guard creation/show foreground loss stops the scene as environment/startup failure; never call SetForegroundWindow on the external window or restore it afterwards. Never SetWindowPos/SetWindowLongPtr on an external HWND.

While the child is hidden, insert it immediately after the exact owned guard HWND with NOACTIVATE/NOMOVE/NOSIZE/NOOWNERZORDER. Both guard and child must be non-TOPMOST; same hierarchy/owner checks apply. Record a read-only complete top-level z list and prove guard rank is above child, including immediate post-call and all post-show samples. Do not rely on a hidden guard, a sentinel insertion handle, activation, or later z correction. If showing the child changes its z position, the first observed order violation is failure, with no repair. External condition remains a geometry/z experiment using the passive owned reference, not a claim to reproduce real VitShell foreground.

### Executable first-visible evidence gate and present limitation

The implementable measurement gate is explicit:

1. Before staging, drain callbacks and record the current exact-generation raw-event sequence boundary. Every own mutation gets begin/end monotonic ticks, arguments/return and native state snapshots under T/P. All SHOW/HIDE/LOCATIONCHANGE/foreground/focus events retain the original event tick and callback receipt tick, exact HWND/PID/object and generation. A SHOW/visible-normal observation before the sole restoring call is an immediate `first_presentation_before_restore` failure. Missing/dropped provenance or generation is coverage insufficient.
2. Immediately before the sole show, require hidden state, staged normal placement and z-order readbacks, fixed identity/monitor/context, and no-child-FG history. Immediately on the returning call, take native T/P geometry/z/FG snapshots before any further native mutation; after show, allow **zero** geometry/style/z mutations until teardown. Every callback and ≥2s sample must retain target rect/order/mode/FG. Any measured small/incorrect normal-visible state fails `first_geometry_fail`; later correct size cannot erase it.
3. Compute event delivery lag and associate each event with the call's tick interval. A callback snapshot describes **receipt-time state**, not event-time geometry. A location/show event stamped before the show-call boundary, generation mismatch, event ordering ambiguity, incomplete start/end markers, gap above the frozen pump bound or API/engine state conflict is coverage insufficient even if final geometry is correct.
4. Strict “the first actual noniconic visible/composited frame was already large” requires a causal observation of geometry/z at that transition, or an independently justified operation contract excluding a smaller intermediate state. Current OUTOFCONTEXT WinEvent gives no historical rectangle or compositor-frame data, and pre/post ShowWindow snapshots leave the cross-process call interior unobserved. **No numerical lag threshold, including a same-millisecond callback, closes that gap.** Thus current channels can prove staged placement and first/retained *observed* geometry, and can falsify strict first-visible behavior, but cannot by themselves produce a strict first-frame PASS. The machine-readable strict result must be `coverage_insufficient/first_transition_geometry_unobservable` when that causal gap remains; do not downgrade the product requirement to “first sampled” or use the elapsed pumping interval as a surrogate.

This last point is a supervisor instrumentation/verification decision before runtime implementation: either supply a separately authorized causal transition evidence mechanism compatible with the no-injection/no-GUI rules, or scope the next measurement as preparation/observed-geometry evidence while retaining strict first-visible as unproven. This plan does not authorize either scope change, suggest a third API candidate, or spend the two-scene budget to rediscover a known evidence gap. No product semantic question needs user discussion; the outstanding question is whether the available apparatus can establish the already specified requirement.
## Frozen runtime envelope (for supervisor review)
At most two fresh children/scenes: synthetic self-owned guard foreground and natural external foreground, one each. Each scene receives a fresh isolated no-autoload/no-plugin/no-extension Godot project and nonce. No replacement run, no third scene, no code/criterion changes after start. First anomaly stops remaining. Natural external unavailable is `not_exercised`; never force another application. Total runtime preparation + execution ≤30 minutes.

Candidate success requires: exact ready nonce/PID/native HWND identity; complete read-only same-PID inventory and CREATE/SHOW generation; documented DPI/coordinate snapshots; safe hidden prestate; staged normal placement already matches chosen monitor work-area target in the declared coordinate context before show; causally evidenced first visible transition normal/noniconic/nonzoomed/nonTOPMOST and within the frozen work-area target (the current passive channels alone cannot satisfy this strict gate); no child foreground/activation/focus and guard/external foreground retained; engine logical mode/size remains internally consistent; all native/engine/foreground evidence continuous for ≥2s. Candidate failures include wrong first-visible geometry, activation/focus, TOPMOST, iconified/nonvisible state, or mode/geometry drift. Observation/identity/DPI/event gaps are `coverage_insufficient`; setup/API/window premise defects are `probe_defect`; environment/child crash are separate; unavailable external is `not_exercised`.

Before any runtime, record: actual GUI binary/version/hash; main/frontend HEAD/status/diff; source/probe/binary hash; full command/exit; remote current-card405 owner reservation and ≤60s process/port check; recents full snapshot + before/after hash; per-child nonce/PID/HWND/inventory/DPI/monitor/placement/style/rect/client/engine records; original raw JSONL/engine log and exact-child teardown; final all-vit/ports-zero; original-byte ZIP/SHA excluding build/binary/cache. No user product semantic discussion is needed: the behavior is explicit. Supervisor must resolve the instrumentation gap above before runtime; this is not authorization to weaken first-visible semantics. Production manager/GD/UI still require a separate revision decision.
