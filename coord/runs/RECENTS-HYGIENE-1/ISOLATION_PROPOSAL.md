# RECENTS-HYGIENE-1 隔离机制建议书（候主管裁定）

- 提出：freeflash 执行流·2026-11-14；依据=本卡取证（FORENSICS.md），不自行改内核/脚本
- 问题一句话：内核把「最近工程」写在**用户级共享文件**（`%APPDATA%\Vit-DAW\global_project_config.json`），且在 open/save/save_as 成功后**无条件**写入（VitHeadlessService.cpp 三处）——烟测装置与用户旅程同权，装置每开一个 fixture 工程就污染一次用户启动面；339 式「后置还原」只能做到会话净差零，还原基准本身含历史污染时污染永续（本卡实测并存实证）。

## 方案 a：烟测装置统一走独立用户配置目录（结构性隔离）

**机制**：给内核加一个用户配置目录覆盖入口——如 env `VIT_DAW_USER_CONFIG_DIR`，`VitGlobalProjectConfig::getConfigFile()` 优先读该 env，未设时维持现行为（fail-open）。装置启动内核时（`dev_agent_smoke.ps1` 等装置 launcher 统一注入，与 VIT309_*/VIT301_GUARD 同款机制）指向 per-run 临时目录；装置 teardown 连目录一起删。

**利**：
1. 结构性根除——污染在写入端就不进用户文件，与脚本纪律、崩溃窗口、并行度无关（治本）；
2. 单点收口——env 在 launcher 层注入一次，各腿脚本零改动；新装置默认继承；
3. 无还原竞态——不存在「teardown 还原覆盖用户在装置窗口内的真实操作」的风险（方案 b 的固有缺陷）；
4. 可推广——该文件将来若承载更多跨会话状态（FE-GUI-START-FEED-1 已建议把 render 产物索引也放这里），隔离面自动跟随；339 的 recents 种子机制改种隔离文件，探针语义不变而更干净。

**弊**：
1. 需要内核改动（小：单方法读 env+目录创建；但按本卡边界须另卡+真栈烟测验收）；
2. 隔离后烟测环境与用户环境出现差异面——须确认无烟测断言依赖用户真实 recents 内容（本卡取证结论：recents 仅被 get_recent_projects 读出呈现，339 greeting 探针属种子机制自种自验，改种隔离文件即可，未发现其他依赖）；
3. 旧二进制/发布版内核不识别 env——装置跑老内核时方案 a 失效，需方案 b 兜底。

## 方案 b：装置腿后置 recents 还原常态化（339 先例升格为装置纪律条款）

**机制**：把 339/340 已两次哈希亲证的模式写成装置纪律（AGENTS §10 精神/装置条款）：凡启动真实内核的装置腿，**启动前快照** global_project_config.json（run 工件留档 before.json）→ **teardown 强制还原**并做哈希一致亲证（还原失败=装置 exit 非零，按环境中断分类，不得静默）。

**利**：
1. 零内核改动，立即可执行；机制已被 339/340 两次真栈验证；
2. 覆盖方案 a 的盲区（老内核、发布版二进制）；
3. 烟测条件与生产完全同构（同一配置路径），无行为差异面。

**弊**：
1. 纪律依赖型——每个装置脚本各自实现，漏一处即漏一世：**本卡清掉的污染正是「先例建立之前」的泄漏**，309 stackleg/govttl 327 两个装置均无还原，洪泛 10 条并挤出用户全部真实工程——机理上证明了纯纪律方案的脆弱性；
2. 崩溃/中断窗口泄漏——env_interrupt、进程被杀等场景 teardown 不执行，污染滞留（339 卡 attempt1 即有 env_interrupt 先例）；
3. 用户操作竞态——装置窗口内若用户真实使用 DAW，teardown 还原会把用户的 recents 新条目一并回滚（用户数据受损）；当前靠「装置窗口内用户不手测」的软约定，无强制；
4. 只保净差、不清洁历史——还原=回到快照（含历史污染），对已污染状态无改善力（本卡并存实证）。

## 建议（候裁定）

**双轨：b 即刻生效 + a 作为结构性收口另卡**。

1. **即刻**：采方案 b 升格为装置纪律条款（决策侧写入 AGENTS §5/§10 或装置纪律文档）：「凡启动真实内核的装置腿=启动前快照+teardown 哈希亲证还原，还原失败非零退出」。此条不涉代码，属纪律面。
2. **另卡（a）**：发内核小卡 `VIT_DAW_USER_CONFIG_DIR` 覆盖（文件域：VitGlobalProjectConfig.cpp/.h + 装置 launcher env 注入 + 一条隔离面烟测断言），验收走既有真栈烟测门槛。a 落地后 b 保留为老内核兜底条款，不撤销。
3. **附带损害处置（需用户/主管裁定，本卡未执行）**：被挤出的用户真实工程 recents 是否重建——候选=$APPDATA/Vit-DAW/projects/ 五项（手测·小星星乐局.vit 等），精确原序不可恢复；若重建建议由主管批准后一次性写入并留 run 工件，或干脆留空由用户自然使用重建。
4. **不主张**：改 maxRecentEntries（10→更大）只延缓不根治，且改变用户可见面行为，不建议捆绑本议题。

## 裁定所需事实清单

- a 的 env 名与语义（fail-open vs fail-closed）由主管定；
- b 条款落点（AGENTS 既有节 vs 装置纪律独立文档）由主管定；
- 用户 recents 重建与否由用户定（涉及用户真实工程偏好顺序）。
