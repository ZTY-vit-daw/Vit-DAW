## 一、用户输入沉淀（设计前，原话）

1. 宿主环境（2026-09-02 问答）：**「浅色」**——Godot DAW 前端为浅色，面板设计置于中性灰底示意。
2. 视觉锚点（2026-09-02 问答）：**「延续 Mondrian 硬边风」**——以现 webui 生效的蒙德里安基因（纸灰 #f4f4f1 / 墨 2px 边框 / 硬投影 / 蓝 #1557d6）为延续锚，非软阴影浅色层。
3. 补充指示一（2026-09-02，原话）：「切记，我们改造的重点就是对话流的动态显示，一定要像codex，zocode，dsh一样是具有动态可执行轨迹显示的。」
4. 补充指示二（2026-09-02，原话）：「如果可以，现在的风格虽然是结构主义，但是我还是想让整体设计往dsh，codex这种风格上靠。」

推论（已执行）：三方向均以轨迹流（交互面④）为设计主角，全部携带终端 agent 实时流式轨迹 DNA；差异在骨架与气质。

## 五、用户选择（2026-09-03 已选定）

- 选择原话：「是的我想要B+C，A的对话流轨迹设计最好，B是我要的风格，C的对话流极简设计的更好。我想如果能够再次融合就更好了。而且我还需要提出一个新的要求，对话流的轨迹需要在输出完成时可以收起来。你再修改一下」
- 解读：**B 的蒙德里安风格为基底** + **A 的轨迹树结构（导轨线串联）** + **C 的极简行式轨迹排版**，三向融合；新交互需求=回合输出完成后轨迹自动收起为回执条（可再展开回看）。
- 后续动作：先出融合初稿 `directions/direction-bc.html` 供确认，确认后展开 `design/gui/templates/` 全套交付（BRIEF §3：主对话视图状态组合 ×1、权限两档态、①②已裁沉淀态、组件级拆解页、设计决策说明）。

## 七、完全档（full access）场景稿（2026-09-03 已产出，待确认）

- 用户需求原话：「很好，但是这是需要我手动确认的权限基础上。如果我要求完全访问，full acesess权限的话是不是就不需要批准这一步了，那整个执行轨迹链条是否就可以保持统一了？你再设计一个这个条件下的情况出来看看」
- 文件：`design/gui/directions/direction-bc-full.html`；截图：`directions/preview-bc-full.png`（首屏·R2 进行中）、`directions/preview-bc-full-mid.png`（链中段·apply 完成 render 接力）、`directions/preview-bc-full-done.png`（完成自动收起态）。三张视觉质检通过。
- 语义回答：**是**——完全档下确认卡整层移除，轨迹链统一为「观察→直接执行→渲染」一条链（一根导轨、一条回执）；判定卡保留（完全档下唯一的人裁环节，人是最终裁决者）；「每步仍可回滚」信任锚权重不降反升（无预批准时回滚即安全网）。
- 设计要点：① 权限默认「完全」激活+副注常显；② 已完成回合收起为「自主执行完成 · N 步」单一回执（对照普通档被确认卡切成两段）；③ 变更类步骤（apply static_eq）蓝节点+「完全档 · 直接执行」标签，原确认卡的假设/预期信息移入该步骤可展开细节（信息不丢失、门没了）；④ 进行中链含「排队中」步骤态——apply 完成瞬间 render 接力 spinner，链不断开；⑤ 完成后自动收起回执条。
- 待办：用户确认本场景稿 → 与 bc 融合稿（普通档）一起作为 templates 双权限档基准展开全套。

## 八、轨迹去边框修订（2026-09-03 已产出，待确认）

- 用户需求原话：「很好很好，然后我想把轨迹的黑色边框去掉，就像C和A那种。只有确定的输入输出带有黑色边框。你试一下看看效果。」
- 改动（`direction-bc.html` 与 `direction-bc-full.html` 同步，双权限档一致）：`.trace-block` 去 `border:2px ink` 与白卡底，轨迹融于纸面（A/C 式）——结构只靠竖直导轨线+节点维持；步骤 hover 加深为 `#ecece6`、展开细节 `.in` 改白底细左线；**黑边体系保留给「确定的输入输出」**：用户消息气泡、确认卡/判定卡（含硬投影）、底部输入框、面板外壳。
- 效果判定（视觉质检三张通过）：轨迹与卡片形成「弱轨/强卡」层级——完成的事沉下去（无边框回执伏在纸面），待裁决的事浮上来（黑边+投影卡片成为唯一行动焦点）；轨迹自身可读性无损（导轨贯穿、节点状态、等宽动作名、时长右对齐）。
- 截图（nb = no border）：`preview-bc-nb.png`（普通档首屏）、`preview-bc-nb-mid.png` / `preview-bc-nb-collapsed.png`（普通档链中段/自动收起）、`preview-bc-full-nb.png` / `preview-bc-full-nb-mid.png` / `preview-bc-full-nb-done.png`（完全档三态）。
- 质检附注两条微观察（非缺陷未处理）：已完成步骤与进行中步骤的正文对比度可再拉开半档；收起回执行与相邻气泡的间距节奏可再均衡。如用户要，展开 templates 时一并调。
- 追加修订（同日，用户原话「轨迹展开后左侧还有一条黑线，也去掉吧」）：`.trace-inner::before` 的 2px 墨色导轨线删除——轨迹结构只靠节点圆点维持（黑实心=完成/蓝实心=直接执行/spinner 环=进行中/灰空心=排队或思考）。截图 `preview-bc-nr-mid.png` / `preview-bc-full-nr-mid.png`（nr = no rail），双稿质检通过：无导轨线残留、行对齐无错位、可读性无损、判定卡黑边+投影无回归。A 版轨迹树基因在融合稿中的最后残留（导轨线）就此移除，轨迹排版完全转为 C 极简行式。

## 九、进入实施前两项同步（2026-09-03 已落地）

- 用户需求原话：「完美。这基本就是我们的目标了。剩下的只有两件事我需要补充同步：1.你要确定输出卡片一定要保有提供给用户进行自定义输入补充的余地，或者卡片交给用户后，选项可以不选，用户直接从对话框重新输入新内容提供给对话流。2.这样改动后要确实分清，输出内容，输入内容是不同颜色的框体，轨迹则是不带框的。这两个问题确定同步后，我们就可以准备进入实际修改阶段了」
- **同步①（卡面自定义补充 + 免选路径）**，双稿一致落地：待裁/待判定卡片（bc：确认卡+判定卡；bc-full：判定卡）按钮组下方新增 `.c-ask` 补充输入行（placeholder「不用选项？直接补充你的要求…」+ 墨底发送键）；两条免选路径都合法——(a) 卡面输入发送 → 内容以用户消息入对话流，卡片沉淀为灰条「已收到你的补充 · 卡面选项未采用」；(b) 不碰卡面、直接在底部对话框输入发送 → 待裁卡全部沉淀为灰条「卡面选项未采用 · 你在对话中继续了」。语义：**选项是加速器不是门槛**；已沉淀卡片不显示输入行（`.card.settled .c-ask{display:none}`）。新增 `.tone-gray` 沉淀色。
- **同步②（框体颜色契约）**：输入=**蓝底框**（新 token `--blue-inp:#dbe6fc`，用户气泡右对齐）/ 输出=**白底框**（卡片族+硬投影）/ 轨迹=**无框**（融于纸面）。契约已写入两稿 `:root` 注释。
- 截图（sync）：`preview-bc-sync.png` / `preview-bc-sync-judge.png` / `preview-bc-full-sync.png` / `preview-bc-full-sync-judge.png`；质检通过：c-ask 行在待裁卡可见且沉淀卡不可见、蓝气泡/白卡/纸面三色一眼可分、无溢出乱码。
- **状态：设计基线冻结**。后续＝templates 全套产出（BRIEF §3 实施蓝图）→ 按 queue 发卡流进入 agent/webui 实际修改阶段（本任务沙箱只写 design\gui\，实改属下一卡）。
